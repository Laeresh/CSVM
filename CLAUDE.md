## Project Description

An XWVM-style remake of **Crimson Skies** (2000, Zipper Interactive, Microsoft): a modern engine that plays the original game using the player's own legally-owned game files. Nothing like this exists yet for Crimson Skies — this is a first-of-its-kind effort.

Charter decided 2026-07-14 (full detail in Claude's project memory):

- **Milestone 1** — complete asset extraction: fill the Crimson Skies gaps in mech3ax (`planes.zbd`, `gamez.zbd`).
- **Milestone 2** — vertical slice: free flight only. One plane, one map (candidate: C1 instant-action arena), arcade controls, original sounds. No AI, objectives, or damage.
- Long-term direction (not commitment): full campaign remake.

## 🚫 Hard rule: no game assets in version control — ever

Public open-source project under the **XWVM legal model**: the repo ships **code and format documentation only**. Game files, extracted assets, ZBD contents, screenshots of hexdumps containing bulk asset data — none of it gets committed or published. The importer reads the player's own install at runtime. `.gitignore` enforces this for `CrimsonSkiesGame/`, `extracted/`, and `tools/`; keep it that way when adding directories.

## Architecture & key decisions

- **Engine:** Godot 4 .NET (C#). Consumes extraction output via mech3ax / Mech3DotNet (strongly-typed C# wrapper).
- **Format reverse engineering:** happens in a fork of [mech3ax](https://github.com/TerranMechworks/mech3ax) (Rust), PR'd upstream to TerranMechworks. Their byte-identical round-trip test harness (extract→repack) is the correctness standard.
- **Flight model:** data-driven approximation — parameterized by plane stats from extracted zrdr reader files, hand-tuned against the original game. No exe decompilation.
- **Division of labor:** Claude writes the Rust parsers, Godot code, and docs; the user reviews, playtests flight feel, and owns upstream/community communication.

## Repo layout

- `CrimsonSkies/` — the Godot 4 .NET project (the actual remake; committed). See "Godot project" below.
- `CrimsonSkiesGame/` — the user's retail game install (git-ignored). ZBD archives in `CrimsonSkiesGame/ZBD/` organized as campaign chapters `C1`–`C5`, each with instant action (`IA1`), story missions (`M0x`), multiplayer maps (`MP1`–`3`). Cutscenes are plain MPGs in `CrimsonSkiesGame/GOSDATA/ASSETS/GRAPHICS/MPG/`.
- `extracted/` — extraction output workdir (git-ignored). Populated by `ExtractAssets.ps1` (below), which mirrors the game's ZBD folder structure: top-level `planes.zip` (unzbd of planes.zbd), `zrdr.zip`, `soundsh.zip`/`soundsl.zip`, `interp.json`, `rimage.zip`, plus per-chapter `C1/gamez.zip`, `C1/texture.zip`, `C1/rtexture*.zip`, `C1/zrdr.zip`, and per-mission `C1/IA1/zrdr.zip` etc. The viewer's defaults read `planes.zip`, `C1/gamez.zip`, `C1/texture.zip`, `zrdr.zip`, `soundsh.zip` — but for each default it **prefers the unpacked sibling folder when present** (e.g. reads `extracted/C1/texture/` over `C1/texture.zip`), so running `ExtractAssets.ps1 -Unzip` (or unzipping just the archives you want to grep in the editor) makes the viewer load loose files and skip zip decompression. All four loaders (`GameZ`, `TextureArchive`, `Zrdr`, `SoundArchive`) accept a zip or a directory; an explicit `--gamez=`/`--textures=`/`--zrdr=`/`--sounds=` is used verbatim.
- `ExtractAssets.ps1` (repo root) — bulk extractor: walks `CrimsonSkiesGame/ZBD`, runs `unzbd cs <mode>` on every ZBD with the right mode for its type (interp→interp/.json; planes+gamez→gamez; soundsh/soundsl→sounds; zrdr→reader; rimage/texture/rtexture*→textures), and writes the output to the mirrored relative path under `extracted/` (basename kept, extension → `.zip`, or `.json` for interp). `cam_anim.zbd`/`mis_anim.zbd` are reported+skipped (mech3ax has no CS anim support). Idempotent (skips outputs newer than their source unless `-Force`); `-Unzip` also expands each `.zip` into a sibling folder; `-Source`/`-Dest` override the roots.
- `tools/` — downloaded binaries (git-ignored): mech3ax v0.6.1, Godot 4.7 .NET editor at `tools/godot/Godot_v4.7-stable_mono_win64/` (`*_console.exe` for CLI use).
- `docs/PLAN-M2-polish.md` — the agreed Milestone 2 polish plan (ordered work items with goal/evidence/approach/verification + status checklist); keep its checklist in sync as items land.
- `OriginalScreenshots/` — user-captured reference screenshots from the original game (committed; UI/plane/sky references for fidelity comparisons — contains no bulk asset data).

## Godot project (`CrimsonSkies/`)

Godot 4.7 .NET, C# / net8.0. Build & run:

```
dotnet build CrimsonSkies/CrimsonSkies.sln
tools/godot/.../Godot_v4.7-stable_mono_win64_console.exe --path CrimsonSkies res://scenes/Main.tscn -- --plane=player_bhawk
```

(First time only: run with `--headless --import` once before running scenes.)

- `src/Mech3/GameZ.cs` — loads a mech3ax GameZ extraction (ZIP or unpacked dir): nodes.json / meshes.json / materials.json into plain C# objects. Parses World partition refs, per-corner vertex colors, per-mesh `lights` arrays (point-sprite lights: the night sky's stars, nav/tower beacons), and the per-polygon **draw priority** (v0.6.1 JSON key `unk04`; upstream mech3ax has since renamed it `priority` — both keys accepted). Each GameZNode records its flat `Index` in nodes.json (= the original's draw order, used as the cross-node layering tie-break).
- `src/Mech3/TextureArchive.cs` — texture lookup over an unzbd texture ZIP **or an unpacked directory** of those PNGs, handles the two name quirks below. Exposes `LastHadAlpha` and `LastAlphaIsSoft` — the latter classifies the alpha channel from the pixels: "soft" means a 0.5-threshold scissor cutout would erase the texture or shred it (max alpha < ~140/255, or partial alpha dominating with few near-opaque texels). True for the original's translucent overlays: baked shadow decals (`bldgshadow`/`abld_shadow`/`lkshad*` peak at ~125/255 — fully invisible under scissor; `thin_shadow` at 155 became solid-black wedges), clouds, prop blur, waterfalls, smoke.
- `src/Mech3/SceneBuilder.cs` — shared GameZ-subtree → Node3D/MeshInstance3D builder: n-gon triangulation, material+mesh caches, keeps only nearest LOD, takes a skip predicate. **Draw-order replication → depth bias (the z-fighting fix):** the original layers coplanar geometry by (1) per-polygon priority, then (2) draw order — polygon list order within a mesh, node order across meshes (nodes.json is a DFS serialization = draw order; later wins under DX7 LESSEQUAL). All three are mapped to a scale-invariant polygon offset: every non-billboard surface uses a generated ShaderMaterial whose vertex shader scales the view-space position toward the eye by `depth_bias + node_bias` — identical projected position, nearer depth. Meshes are split into one surface per (material, priority) in first-occurrence order; `depth_bias` = priority × `DepthBiasPerLevel` (2e-4, TUNE) + surfaceRank × `SurfaceRankBias` (2e-6, capped at rank 5 — the within-mesh tie-break: gyro canopy lattice over fuselage skin, tile roads over tile grass); `node_bias` (an `instance uniform`, set per MeshInstance3D — needs Forward+) = GameZNode.Index × `NodeOrderBias` (5e-8 — the cross-node tie-break: airfield apron detail over base tile, road decals over rail decals). Negative priorities push away (skydome −49, zeppelin gasbags −10, pilot body −1). The shader mirrors StandardMaterial3D's look (vertex-color × texture albedo, cull disabled, unshaded when fullbright, Burley/GGX + roughness 0.85/metallic 0/specular 0.5 when shaded; opaque/scissor/blend fragment variants) and is cached per feature combo; materials cache per (material, priority, cappedRank). Billboard (cloud-sprite) materials stay StandardMaterial3D — no bias, nothing coplanar to fight. **Sidedness:** `cullBackfaces: true` (used by PlaneBuilder) additionally splits surfaces by the per-polygon SHOW_BACKFACE flag (`unk2` in v0.6.1) and backface-culls the single-sided ones — `cull_front`, because the source's visible side is where the vertex loop runs counter-clockwise (right-handed) while Godot front faces are clockwise. This is what hides the autogyro's inward-facing interior frame lattice (`agyro_cock1` bulkheads in the `tail` mesh) so its aft fuselage shows yellow skin with openings, like the original. No plane node has a mirrored (negative-determinant) transform, so the blanket cull direction is safe. The world builder still renders everything double-sided (cull-disable) — switching it to per-polygon culling is a candidate cleanup, unvalidated. Known accepted limit: the tie-break hierarchy is approximate for extreme node-index spans (a prio-0 node >~4000 indices later can out-bias a prio-1 overlay; no such pair observed in C1), and cross-node deltas of ±2 indices sit at interpolation-noise level (one 6-poly rail/transition patch NE of the C1 bridges). **Alpha handling:** textures whose alpha is "soft" (see TextureArchive.LastAlphaIsSoft) alpha-blend automatically — this is what renders the baked shadow decals correctly (they were invisible or solid black under scissor) — in addition to the caller's explicit `blendTexture` predicate; other alpha textures scissor (hard cutout — fences, trees, railings). `fullbright: true` renders unshaded (texture × baked vertex color — the original engine's world look). `generateCollision: true` attaches a static trimesh collider (`StaticBody3D` + `ConcavePolygonShape3D`, cached per mesh, `BackfaceCollision = true` because the source winding is inconsistent) to each mesh; a `collisionSkip` predicate exempts subtrees (renders but not solid). The explicit `blendTexture(name)` predicate still promotes chosen alpha textures to `Alpha` blending on top of the automatic soft-alpha rule (WorldBuilder passes it for the clouds, PlaneBuilder for the `*blur*` discs — both are also caught by the classifier, so the predicates are now belt-and-braces). Only consulted for textures that actually carry alpha, so opaque cloud/sky (`cloudlayer`/`sky*`) is unaffected. A second optional predicate `billboardTexture(name)` renders the matching meshes as camera-facing billboards (the cloud *sprites* — flat 2D cards in the source): the material gets `BillboardMode.Enabled` and the mesh is recentered on its own quad centroid (offset stored per mesh, re-applied as each instance's local position) so the billboard pivots at the quad center, not the node origin — the source sprite quads sit up to ~650 units off their origin, so without recentering they would swing around as the camera turns. Recentering also tightens transparent sorting (each sprite sorts by its true center). Meshes with `lights` additionally get a POINTS-primitive instance: fixed-pixel additive dots (3 px — the source size params 0.17/30/4000/6000 are undecoded), never collidable/shadowed; black effect-prototype lights add nothing and stay invisible. **Distance fog:** the original's fog volume is a vertical **cylinder** around the camera, not a sphere (user-diagnosed 2026-07-17): the generated shader mixes ALBEDO toward the fog color by **horizontal** (x/z) camera distance, scaled by an altitude fade — full fog below `FOG_ALTITUDE`[0], none above [1] — so the overcast deck/sky overhead stays clear instead of graying out (zone1's altitudes 970→1047 = exactly cloud-band bottom → whiteout-band centre; zone2's 4000→5000 > flight ceiling = night fog at every flyable altitude). Implemented per-fragment: `INV_VIEW_MATRIX` lifts the view-space VERTEX back to world space for `distance(world.xz, CAMERA_POSITION_WORLD.xz)` and the fragment-altitude fade. Driven by three **global** shader params `csky_fog_color`/`csky_fog_range` (near/far)/`csky_fog_alt` (full-below/none-above) that PlaneViewer registers + sets once per flight from weather.json (no-op range when not flying, so static viewing is unfogged), plus a per-instance `csky_fog_on` (default 1) so the caller can opt a subtree out — WorldBuilder sets it 0 on the camera-anchored skydome, whose below-horizon skirt would otherwise fog solid gray at ~22 km. The aircraft shares the term but is a no-op at chase distance (always within the near range).
- `src/Mech3/PlaneBuilder.cs` — thin wrapper: builds one aircraft, skips cockpit/destroyed/shadow subtrees, plus every plane's `*_hook` skyhook subtree (`blood_hook`, `kest_hook`, `gyro_hook`, … — retracted by default: each `*_hook.json` anim's RESET_STATE deactivates the group + its arm/door nodes; `player_hook.json`'s `player_extend_hook` extends it only for zeppelin docking). Shaded (dynamic lighting). Builds its SceneBuilder with `cullBackfaces: true` (see SceneBuilder — aircraft interior structure must be backface-culled or it paints over the skin). **Damage panels (fixed 2026-07-16):** every player plane's top LOD has a `player_damage_on` group holding `pdp1`–`pdp8` (damage-state panels, `damage1/2.tif` torn-skin textures — start INACTIVE per `player_destruct_reset.json`'s `plane_reset` anim) *and* `pdp2_h`/`pdp3_h` (the matching HEALTHY panels, ACTIVE at reset — real airframe sections: the Bloodhawk's wingtips, the Kestrel's outer wing thirds with the roundels). PlaneBuilder skips `pdpN`/`pcdpN` (digits-only suffix) but renders `pdpN_h`; the sibling `player_damage_off` group (intact duplicates `pdp2i`/`pdp3i`, the original's vehicle-damage-detail-OFF variant) is skipped wholesale. The old code skipped `player_damage_on` entirely, which amputated the `_h` panels (Bloodhawk flew without wingtips, Kestrel without outer wings). Propellers are handled via `PropParts` (below): the default exterior build keeps the still `staticpropN`/`staticrotorN` disc and hides the blur layers; the `spinningProps: true` build (free flight) does the reverse — hides the static disc, keeps the `propN`/`propNb` (+ autogyro `rotorN`/`rotorNb`) blur layers for a `PropAnimator` to spin (`nitropropN` stays hidden either way — no nitro system yet; hiding it in flight is also load-bearing visually — it is a NON-spinning blur disc, so leaving it in overlays a fixed disc on the spinning ones whose edge paints a 1px seam that shimmers as the camera moves). It also passes SceneBuilder a `blendTexture` rule for the blur textures (`*blur*` → `rotorblur`/`zeprotorblur`): those discs are soft sprites whose alpha peaks at ~26%, so the default 1-bit AlphaScissor cutout erased them entirely (looked like a missing/frozen prop) — alpha-blending them (as with the clouds) restores the translucent spinning-disc, clearly visible against bright sky and subtly over dark terrain, as in the original. **Wing-light flares (2026-07-16):** after building, `Build` collects each plane's `wing_flare1`/`wing_flare2` wingtip sprite quads (see `WingLights`), builds them **hidden** (the original's `wing_light.json` RESET_STATE starts them off), and re-skins each glow quad (`oil_liteflare.tif`) with a shared additive, camera-facing **billboard** material tinted the data's warm amber (LIGHT_STATE COLOR 0.88/0.78/0.36) — the source quads are one-sided, so previously the flare only showed from behind. The collected nodes are exposed as `WingFlares` for a `WingLightBlinker` (flight only) to flash; the static viewer leaves them off. Only planes with the nodes get flares — the Bloodhawk and autogyro have none in the data.
- `src/Mech3/PropParts.cs` — classifies a plane's propeller/rotor subnodes by name (`staticpropN`/`staticrotorN`, `nitropropN`, `propN`/`propNb`, `rotorN`/`rotorNb`) and gives each spinning kind its local spin axis + rate. Rates are the `XYZ_ROTATION` values from the original's prop animations — `plane_props.json` (a single shared "warhawk" `spinprops` def that vehicle.json wires to every plane via `spin_props_anim`) and `autogyro.json` (`agyro_rotors`, the autogyro's override): propeller discs spin about local **Z** (the nose axis) — `propN` −220, `propNb` +60 (a fast blur disc + a slower counter-rotating ghost); the autogyro's overhead `rotorN` spins about local **Y** — `rotor1` +165, `rotor1b` −60. Axis choice is corroborated by mesh geometry (prop discs lie in the XY plane, the rotor disc in XZ). Units are undecoded in the source; treated as degrees/second — a visual TUNE (a blur disc reads as spinning at any smooth rate; the real prop turns a slow ~0.6 rev/s, not fast).
- `src/Mech3/ControlSurfaces.cs` — control-surface *mesh*-node classifier + hinge axes (M2-polish item 7). Every player plane names its movable surfaces uniformly in planes.zbd: the deflecting mesh node (`l/r_aileronN`, `l/r_elevatorN`, `l/r_rudderN`, the Fury's `l/r_rudder_rotate`) hangs under a hinge parent group (`lailerN`/`railerN`, `lft_elev`/`rt_elev`/`l_elev`/`r_elev`, `lrudderN`/`rrudderN`, bare `l_rudder`/`r_rudder`, the Peacemaker's `r_rudder1b`) whose transform places/orients the hinge line; the parent names deliberately do NOT classify (rotating both would double the deflection — digits are required on the bare `l_rudder` form for exactly this reason). Hinge axes corroborated against mesh geometry: aileron/elevator meshes are spanwise slabs (wide local X, chord aft +Z, hinge through the node origin) → hinge about local **X**; rudders are vertical fins (flat in X) → local **Y**. No zrdr anim/reader defines deflection — the original drives these procedurally, so angles/rates are TUNE in ControlSurfaceAnimator, not data.
- `src/Mech3/WingLights.cs` — the single source of truth for wingtip nav lights: the flare-node predicate (`wing_flare1`/`wing_flare2`), the glow texture (`oil_liteflare`), the warm-amber flash color (`0.88, 0.78, 0.36` = `wing_light.json`'s LIGHT_STATE COLOR), and the blink period (1.5 s = its LOOP SEQUENCE_OFFSET). PlaneBuilder uses it to hide + re-skin the flares (see PlaneBuilder); `WingLightBlinker` uses it to flash them. Documents that `oil_liteflare` is also used by a few real airframe meshes, so the additive-billboard treatment is scoped to the flare **nodes** by name, not routed through the texture (else those meshes would be wrongly recentered/billboarded).
- `src/Mech3/WorldBuilder.cs` — builds a whole chapter world (fullbright): World children + partition-referenced subtrees; skips `horizon` (built separately, see below), `fvol*` (flight-boundary volumes), `dzpaths` (path ribbons). A shared `IsCloudOrSkyTexture` predicate (`cloud*`/`sky*`) classifies cloud/sky surfaces by **texture** (node names are unreliable; cloud layers appear under generic names like `g27517`), and two callers use it: `collision: true` (passed only when flying) generates static colliders for solid geometry but exempts those surfaces (non-solid), and it is passed to SceneBuilder as the `blendTexture` rule so the clouds alpha-blend instead of scissor. Only cloud1/cloud2 (RGBA) actually blend; the opaque Sky1.tif skydome walls and `cloudlayer` deck have no alpha and stay opaque (which keeps the 2.5× camera-anchored dome depth-writing behind the blended clouds). A narrower `IsCloudSpriteTexture` (`cloud*` but not `cloudlayer`) is passed as SceneBuilder's `billboardTexture` so the soft cloud sprites (cloud1/cloud2 — vertical 2D cards) face the camera, while the horizontal `cloudlayer` deck sheets stay flat. **Cloud deck split:** the `cloudlayer` deck (the opaque overcast sheet — in C1, 144 top-level 1024-unit tiles at y=960 covering the whole map) is collected by `IsCloudLayerDeckNode` (texture `cloudlayer`) into a separate `CloudDeck` node (kept a child of the world root at identity so its tiles keep their world positions) instead of the static world root; PlaneViewer moves it each frame to follow the player. The cloud1/cloud2 sprites stay in the world root (world-fixed). `MeshUsesTexture(node, predicate)` backs both this and `NoCollisionNode`. `BuildHorizon(zone)` builds the original skydome as a separate camera-anchored backdrop node (default `zone2` = night, the sky the original shows at the C1 airfield): never collidable, never casts shadows (it covers the whole sky and would blacken the world). The `moon` quad is rebuilt as a camera-facing billboard (`BillboardKeepScale` — plain billboards ignore the dome's 2.5× scale) with its uniform background (66,73,99) color-keyed to alpha; original screenshots show a round moon from any heading with crater detail and no quad edge, ruling out both a static quad and additive blending. `DisableFog` walks the built dome and sets SceneBuilder's `csky_fog_on` instance uniform to 0 on every MeshInstance3D, opting the dome out of distance fog — **currently disabled by an early `return` (user change with the 2026-07-17 fog remodel): the dome now participates in fog**, which the cylinder model makes correct — high dome fragments stay clear via the FOG_ALTITUDE fade while the horizon band fogs toward the same gray as the terrain fog wall.
- `src/Mech3/Clutter.cs` (`ClutterBuilder`) — the original's **clutter system**: forest trees on forest-textured hillsides, bushes along the rivers (M2-polish item 5). The gamez has no placed tree nodes — each chapter's boot script (interp.zbd → `support\<chapter>\adjust.gw`) registers clutter **templates** (`AddClutterTemplates terpat02`) that the script `LoadGameGen`s into the gamez as parentless, UNREFERENCED subtree roots (why WorldBuilder's placed-node walk never sees them; they sit among the effect prototypes). A template = a flat ground quad whose **texture names the terrain texture it decorates** (terpat02.tif = C1's forest texture) and whose **size is the tiling period** (512 m for C1 terpat02; the `terpat01-128`-style variants elsewhere are 128 m ones with their own `-128.tif` texture), plus decoration children: single vertical one-sided quads (firtree1/2 17.8–20.9 m, dougfirtree1 22.5 m, bush1/2) each with a local position on the patch. `TemplateNames(interpPath, chapter)` reads the chapter's AddClutterTemplates list from `extracted/interp.json`; `Build(names, collision)` stamps each template across every placed world polygon textured with its ground texture (same walk as WorldBuilder: world children + partition refs, nearest LOD only, same skips). The original's exact alignment is undecoded and the world's UV tiling is wildly non-uniform (256–1280 m/repeat on hillsides), so placement tiles a fixed **world-space X/Z grid** of the template's period instead — authored density everywhere, seam-consistent across polygons (one global grid), each sprite planted at the polygon's barycentric surface height (fan/strip triangulation mirroring SceneBuilder). Slopes steeper than ~75° and degenerate XZ triangles grow nothing; a rounded-position set dedups decal-layered coplanar polys. C1 places 9,303 sprites (~9k firs + river bushes). Rendering: ONE `MultiMeshInstance3D` per decoration kind, a hand-rolled **Y-axis-billboard** shader (upright, spins about the planted point toward the camera — the source cards are one-sided, so the original must face them too), fullbright like the world, alpha-scissor cutout, and the same cylindrical distance-fog term as SceneBuilder's shader (trees fog with the terrain they stand on). Collision (flight only): one static trimesh (`clutter_col`) of two crossed vertical quads per sprite, BackfaceCollision — trees are hittable like the original (`spruce_destroy1/2.json` exists; destruction is dogfight-milestone work). C2/C5's city-block templates parse through the same code but their non-quad decorations are logged + skipped (future work).
- `src/Mech3/Zrdr.cs` — zrdr extraction reader (`Zrdr.LoadFile` from zip or dir + `ZrdrDict` view over the alternating key/[values…] reader lists).
- `src/Mech3/WavFile.cs` — pure-C# WAV parser (no Godot deps) with MS ADPCM→PCM16 decoder; the game's WAVs are MS ADPCM (fmt 2, 4-bit, 22 kHz), which Godot can't load natively. Decoder verified byte-identical against an independent Python implementation.
- `src/Mech3/SoundArchive.cs` — WAV lookup over a soundsh/soundsl extraction (zip or dir) → cached Godot `AudioStreamWav` (forward loop when the sound def says LOOPED).
- `src/Mech3/SoundDefs.cs` — sounds.json SETS parser: `snd_*` name → `SoundDef` (wav, LOOPED/3D/FREQUENCY flags, RANGE, VOLUME).
- `src/Flight/PlaneStats.cs` — typed flight stats for one player plane from vehicle.json (`dynamics` block through the `kind_of` chain) + engines.json (stock engine power) + player.json globals, plus sound: the plane's `engine_sound` def name and the player.json volume/pitch `SoundCurve`s (clamped two-point ramps).
- `src/Flight/SpawnPoints.cs` — reads the flight spawn from a **mission's own zrdr** (in `extracted/<chapter>/<mission>/zrdr/` — a different archive than the shared `--zrdr`), two schemas both yielding `SpawnPoint(Position, HeadingDeg)`. `LoadIa(missionZrdrPath, scenario)`: instant-action `ia.json` `spawn_points` for a scenario (`zeppelin_run`, `dogfight_ace`, `dogfight_squadron`, `stunt_flying`, …), each spawn `[x, y, z, heading°]` — only IA1 folders have ia.json; the original picks one at random per launch. `LoadPlayerInit(missionZrdrPath)`: story-mission `objectives.json` `PLAYER_INIT` (`[1, [x,y,z], [pitch,yaw,roll]°, throttle, speed]`), taking position + yaw. PlaneViewer's `ChooseSpawn` tries `LoadIa` first (random pick, or `--spawn=N` forces one), falls back to `LoadPlayerInit` (M0x missions), then a fixed C1 spawn; `LogSpawn` turns the heading into a level look-at via `Basis(Up, heading)` and logs it. Throttle/speed from the data are ignored — the remake uses a fixed start (FlightController).
- `src/Flight/Weather.cs` — `WeatherState`: per-mission atmosphere from the flown mission's own `weather.json` (same archive as SpawnPoints' ia.json/objectives.json). Parses per-zone distance fog (`FOG_COLOR`, `FOG_RANGES` near/far, `FOG_ALTITUDE` low/high — the fog cylinder's vertical extent: full fog below low, none above high; see SceneBuilder's fog bullet, `CLIP_RANGES`), the `CLOUD_COVER` whiteout band (TOP/BOTTOM/THICKNESS), and `WIND` (static + random-gust bounds — drives the ambient cloud-puff drift, see CloudPuffs.cs). weather.json is one alternating dict, but the `CLOUD_COVER`/`WIND` blocks pair keys with **bare scalars** (`"TOP", 1124`) not lists, so `ZrdrDict.FromAlternating` (which needs list values) can't read them — they're walked as raw key/next-element pairs; the per-zone blocks are all list-valued and go through the normal dict. `Fog(zone)` returns the zone's fog (a no-op fog if absent — near/far so far out nothing fades); `WhiteoutAmount(altitude)` is the 0..1 overlay opacity — a symmetric trapezoid (user-observed in-game): clear sight (0) at BOTTOM and TOP, ramping linearly to a fully-opaque core (1 — the plane vanishes) that is THICKNESS deep and centred on the band midpoint (so THICKNESS is the opaque-core depth, **not** an edge transition; C1/IA1 970–1124 ±30 → total only in 1032–1062). Which zone a mission shows isn't in these readers — the remake picks it via `--sky-zone` (default zone2 = night). PlaneViewer feeds the fog into global shader params and the whiteout into a full-screen overlay (see those bullets).
- `src/Flight/FlightAudio.cs` — own-plane sound loops (non-positional): per-plane engine WAV with throttle-driven pitch 0.6→1.0, overspeed whine (`prop_sound` curves, silent below fd_speed), airframe rattle (`rattle` block, volume 0→1 over 1.0–1.2× fd_speed). Driven per-frame from FlightController (not while crashed) — `Update(dt, …)` takes the frame delta to advance the engine-start envelope. **Prop start/stop one-shots** (`snd_propstart`/`snd_propstop`, both non-looped, no VOLUME → base gain 1.0): `StartEngine()` plays `snd_propstart` and (re)sets a 0→1 gain envelope (`EngineStartRamp` 1.8 s) that the engine loop fades in behind — matching the original's ~1.5–2 s prop-start fade instead of the loop snapping in at full volume. It fires on the initial spawn (`_Ready`) and on every respawn via the loop-restart hook in `Update` (when `_engine` isn't playing, i.e. after a crash stopped it — the "natural hook"). A single `_engine` player means the restart can't double the loop. `OnCrash()` kills the loops and fires one of the game's plane-explosion one-shots (`snd_exp_plane1..4`, random pick). `OnEngineStop()` is the `snd_propstop` capability (plays the wind-down + kills the loops) — **deliberately not called on crash** (the explosion covers that moment; a wind-down under it would read wrong) and wired for a future landing/shutdown flow, which must also stop driving `Update` (like the crash freeze) or the restart hook would re-fire propstart. `--mute` suppresses everything (PlaneViewer never constructs FlightAudio).
- `src/Effects/Puffer.cs` — the original engine's billboard-particle emitter, data-driven from a zrdr `PUFFER_STATE` block. `PufferState.Load(zrdr, file, name)` DFS-searches an effects reader (flame_ball.json, fire.json, pufftrails.json, … same schema) for the fully-defined puffer (has `NUMBER`, not a stop-stub) and parses its params (per-axis random velocity, friction, size/lifetime ranges, growth factor, deviation, and the `TEXTURE_SEQUENCE` flipbook). `Puffer.Create(state, textures)` builds a horizontal atlas from the flipbook PNGs and returns a CPU-simulated emitter drawn as ONE `MultiMeshInstance3D` (per-instance transform + custom data): a small spatial shader billboards each quad toward the camera (hand-rolled billboard_keep_scale, since MultiMesh has no built-in), picks the flipbook column from `INSTANCE_CUSTOM`, and additively blends (`blend_add`, `depth_draw_never`) — the fire frames are alpha-masked with black edges, so additive gives a soft glow and no quad edge. The CPU sim honours the reader exactly: exponential friction, `Lerp(1,growth,age/life)` size growth, and the non-uniform per-frame flipbook timing; a life-fade envelope (`FadeIn`/`FadeOutStart`) is the only render nicety not in the data. `Burst(worldPos)` (sets `TopLevel` so it stays put in world space) emits `Number` sprites per `TimeInterval` for the caller's active window (default 0.3 s = large_fireball's STOP time); `Clear()` wipes all live particles. Reusable for the future dogfight effects.
- `src/Effects/CloudPuffs.cs` — the ambient cloud puffs: a field of very soft, translucent `cloud1`/`cloud2` billboard sprites the plane flies through at altitude (the wisps drifting past in `OriginalScreenshots/C1 IA1 Cloud Puffs and Moon.png`). **Why synthetic, not the world's own sprites:** C1 places ~600 `cloud1`/`cloud2` sprite quads, but they are **clustered near the airfield** (verified — two far map corners at band altitude render bare) and world-fixed, so most of the map has no clouds at altitude. No zrdr defines an ambient emitter (only crash-style `PUFFER_STATE` readers exist), so this is a hand-tuned field parameterized by the data we do have: the `CLOUD_COVER` band anchors the layer's altitude, the weather `WIND` drives a slow drift (every feel constant is TUNE, playtest-calibrated). **Model:** a fixed pool of world-anchored sprites in a cylindrical shell around the camera, **anchored in Y to the cloud band** (world-fixed altitude — you climb up into the layer then out over it, like a real layer) while the field follows the plane in X/Z; a puff the plane flies past horizontally recycles to the leading edge (spawns ahead of the nose so the plane flies into fresh clouds), so the field is endless. Alpha fades to 0 at the shell edge (recycled puffs fade in, never pop) and by vertical distance from the camera (`VertFull`/`VertFade` — clear well below/above the layer, so low-altitude flight has no clouds and climbing above leaves scattered wisps below). Drawn as ONE `MultiMeshInstance3D` (one draw call): a spatial shader billboards each quad toward the camera (hand-rolled keep-scale, like Puffer), applies a per-instance roll (variety), picks cloud1/cloud2 from `INSTANCE_CUSTOM`, and **alpha-blends** (`blend_mix`, `depth_draw_never`, `fog_disabled` — soft translucent clouds, unlike Puffer's additive fire glow). The cloud textures are fairly opaque (mean α≈0.43, p90≈0.87), so overlaps saturate fast — `BaseAlpha` is kept low (0.06–0.13) so they read as translucent veils not a solid white ring; `Count` 12, `Radius` 620 m. `Create(textures, wind, bandBottom, bandTop)` builds the 2-frame atlas (null if the textures are absent); `Update(dt, cameraPos, cameraForward)` advances the field each frame (self-gates via the vertical fade — safe to call at any altitude). PlaneViewer builds it in `SetupWeather` (only when the mission has a `CLOUD_COVER` band) and drives it in `_Process` from the flight camera. `--fly`, or static `--chapter` + `--sky-zone` for deterministic `--campos` verification.
- `src/Flight/FlightModel.cs` — arcade flight dynamics, reworked 2026-07-17 into a **velocity-vector model in arcade clothing** (M2-polish item 6 + the user's "no lift — the plane hovers at 0 mph" report; the standard simple-flight-model decomposition, cf. brihernandez's ArcadeJetFlightExample / Vazgriz's Unity flight sim). Body rates from control torque × reciprocal inertia vs `ang_momentum_damp` (unchanged). Translation (**vector integration, 2026-07-17 second pass**): thrust (along the nose), drag (against the motion) and gravity integrate on the velocity **vector** `v = VelocityDir·Speed`, so the speed can pass **through zero** — a vertical zoom tail-slides out downward instead of freezing mid-air at a clamped 0 (user-reported: plane stopped in the air with the HUD mph creeping back up; the first-pass scalar model clamped `Speed ≥ 0` and re-accelerated along a stale path direction). **Lift fraction** = `min(1,(v/liftSpeed)²) × |planeUp·worldUp|` (wingVert — 1 level *or inverted* (arcade), 0 knife-edge); gravity is split about the path and its **cross-path component is canceled by the lift fraction** — the deficit is the sink: vanishes at full lift, drops the plane when slow or knife-edge. The **nose-chase alignment** (velocity slerps toward the nose) scales with airspeed (controls mush as airflow dies) *and* wingVert (`KnifeAlignFloor` 0.35 — the chase is the lift force turning the velocity, so knife-edge equilibrium sits visibly ~10° below the nose: the sink). **Stall** (below 0.3·fd_speed): the nose is pulled toward **world-down** via a great-circle rotation about nose×down (attitude-independent — works inverted; replaces the old body-frame pitch-rate bias), rate `stall_mag × StallNoseRate × depth` — deep-stall rate exceeds full-elevator authority, so the drop is decisive until airspeed recovers. **While stalled the nose can NOT be raised over the horizon at any bank angle** (original behavior, user-observed 2026-07-17): after the frame's rotations its world elevation is capped at `max(horizon, frame-start elevation)` — pulled up from below it parks at the horizon; caught nose-high by the stall it can only come down (so a low-speed full-pull loop breaks at the top instead of completing). **Drag is a quadratic + linear blend** (`LowSpeedDragBlend` 0.35 TUNE, normalized so drag(fd_speed) = max thrust — the full-throttle equilibrium stays exactly `fd_speed` for any blend): the linear share is the low-speed air-resistance bite (user-reported: idle level flight barely decelerated on the pure-v² tail; now 120 mph idles down to the ~89 mph stall in ~9 s and settles into a natural nose-dropped glide). **Climb retention**: gravity's along-path bleed is scaled `ClimbGravityScale` 0.6 when climbing (full when diving) — an 11° full-throttle Bloodhawk climb holds ≈122 m/s; the exact factor awaits the user's measured original-game climb curve. Verified via segmented `--hold` telemetry runs: vertical zoom → 12 m/s → nose-over → dive recovery (no hover); knife-edge path −10°, −174 m in 15 s; cruise/level regression byte-identical behavior (wingVert 1 → all new factors are exactly 1). Hand-tuned scale constants marked TUNE.
- `src/Flight/PropAnimator.cs` — spins the flying aircraft's propeller/rotor blur discs. `Build(planeModel)` walks the built tree, collecting every node `PropParts` classifies as a spinning kind with its local axis + rate (null if the model has none); `Advance(delta, speedFactor)` rotates each about its own local axis (`RotateObjectLocal`, so the disc always spins in-plane regardless of parent orientation). FlightController advances it each frame with a throttle-scaled factor (`PropIdleSpin` 0.4 floor so discs still turn at idle; 0 while crashed). Cheaper than an AnimationPlayer. Only used in `--fly`; the static `--plane` viewer keeps the still disc.
- `src/Flight/ControlSurfaceAnimator.cs` — deflects the flying aircraft's ailerons/elevators/rudders with stick input (M2-polish item 7; PropAnimator-style: `Build(planeRoot)` collects every node `ControlSurfaces` classifies, null if none — the autogyro has only its 2 ailerons; `Advance(delta, input)` slews, `Reset()` neutralizes). Unlike the props' incremental spin, deflection is an **absolute pose**: each surface stores its build-time local basis and gets `Basis = base · Rot(hingeAxis, angle)`. Three channels (pitch/roll/yaw) slew toward the stick at `SlewPerSec` 3 /s (TUNE); max ±20° per kind (TUNE). The per-surface sign bakes (1) the stick convention — ailerons opposite per side (roll left = left TE up / right TE down), elevator/rudder TE against the commanded rotation like real linkages (pull = TE up, yaw left = TE left); (2) a **canard flip**: hinge z < `CanardMaxZ` −1 m ⇒ nose-mounted (the Bloodhawk's elevators, z −4.2) ⇒ pull deflects TE-*down*, the lift-raising direction (every conventional tail surface sits at z ≥ 0.19); (3) a **frame flip** = sign of the accumulated hinge axis · its canonical direction in plane space (the Bloodhawk canard groups are mounted yaw-π, so their local X points left). Driven from FlightController's `_Process` with the physics frame's input (`_lastInput`), frozen while paused (the paused orbit camera can inspect a held deflection) / crashed, reset on respawn. `--fly` only; the static viewer keeps surfaces neutral. Verified via A/B screenshots (1 s neutral then input, shot 0.25 s later — near-identical viewpoint): aileron pair opposite + correct, Kestrel tail elevators TE up on pull, Bloodhawk canards TE down; counts Bloodhawk 5 / Kestrel 6 / autogyro 2.
- `src/Flight/WingLightBlinker.cs` — flashes the flying aircraft's wingtip flares on the original's 1.5 s cycle (PropAnimator-style: a flat list of nodes the flight loop advances). `Build(flares)` takes PlaneBuilder's `WingFlares` (null if empty, so callers skip it); `Advance(delta)` shows them only during a short window (`FlashDuration` 0.08 s, TUNE — the source flash is a single frame, widened so the blink reads crisply) each `WingLights.BlinkPeriod`; `Reset()` (called on respawn) restarts the cycle with the flares off. FlightController advances it each `_Process`, frozen while paused (deterministic screenshots) and crashed (airframe hidden). Only used in `--fly`.
- `src/Flight/FlightController.cs` — flying-aircraft node: keyboard + gamepad → FlightModel → transform, roll-following chase camera, text HUD (mph/ft/throttle + stall warning), telemetry print 1/s (pos/speed/throttle/rates + `path`/`nose` climb angles and `wv` wing verticality — the flight-model verification readout). Scripted runs use `HoldSegments` (from `--hold`): a sequence of (input, duration) segments advanced by sim time — the last segment holds forever, respawn restarts the sequence (deterministic cyclic runs). **Chase camera** (`UpdateChaseCamera`): position is lerped (`CamSmooth` 8 /s) toward a behind-and-above offset expressed in the plane's *own* frame (`DesiredCamPos`, `camUp = Attitude.Y` — full bank-follow), and the camera **basis** is slerped (`CamRotSmooth` 7 /s, TUNE — a little roll lag reads dynamic) toward a `Basis.LookingAt` of the point ahead of the nose with the plane's up, so **inverted flight shows the world upside down** and the horizon rolls smoothly through 360° with no snap at ±90°. Smoothing the basis (not re-deriving a hard LookAt from a near-world up each frame) is the fix; a dot-product guard falls back to world-up if the view ever runs ∥ to the plane's up (never happens in practice — up ⟂ nose). `SnapCamera` (spawn/respawn) sets orientation instantly, so no slerp transient on (re)spawn. `Setup(model, camera, spawnPos, spawnLookAt)` seeds the spawn; `Respawn` starts every (re)spawn at **0.5 throttle / 53.6 m/s (≈120 mph)** — matching the original's instant-action start (user-observed), from which the plane accelerates toward cruise (`SpawnThrottle`/`SpawnSpeed` constants, replacing the old 0.8·fd_speed). The spawn position/heading come from the mission's ia.json via PlaneViewer (see `SpawnPoints.cs`). Ground/object collision: each physics frame casts a ray along the frame's flight path (prev→next, extended one airframe-length past the nose) against the world's static colliders; a hit crashes the plane — the crash log names what was hit (`CRASH into <parent>/<body>` — terrain tiles read like `g314/col`, the tree field `world1/clutter_col`) — explosion one-shot + the game's `large_fireball` at the ray's impact point (`CrashEffect?.Burst`, cleared at respawn), airframe hidden, frozen at the impact point with a "CRASHED — PRESS R" HUD banner until R (or gamepad Y/A) respawns (`--hold` runs auto-respawn after 1.5 s so scripted flights keep going). `DebugCollision` (from `--debug-collision`) draws the swept collision ray + a cross at the probe tip (green; freezes red at the impact). Backstop respawn when under the map (y < 60) if the swept ray ever misses. Also advances the `PropAnimator` (propeller/rotor spin) each `_Process`, throttle-scaled (frozen while crashed), the `WingLightBlinker` (wingtip flare blink, frozen while paused/crashed, reset on respawn), and the `ControlSurfaceAnimator` (aileron/elevator/rudder deflection from the physics frame's stick input, frozen while paused/crashed, neutral on respawn). **Debug pause** (P, or gamepad Start; edge-detected toggle): freezes the whole sim in place — physics, input, collision, audio update, prop spin, and wing-light blink all halt, HUD shows a ⏸ banner — so successive screenshots frame the plane from the same position. While paused the chase camera is replaced by a **free orbit** around the frozen plane (`SeedOrbit`/`UpdateOrbitCamera`, seeded from the chase pose so there's no jump): WASD/arrows swing azimuth/elevation, Shift/Ctrl (or gamepad left stick + triggers) dolly in/out — so you can circle the plane and shoot any angle of the same pose. Gamepad (first connected joypad): left stick pitch/roll with 0.15 deadzone + squared response, LB/RB rudder, RT/LT throttle up/down, Y respawn, Start pause.
- `src/PlaneViewer.cs` — Main.tscn root script: orbit camera, lighting. **F12** (any mode — orbit view or free flight) saves the current frame to a timestamped PNG under the repo's git-ignored `Screenshots/` folder (`SaveScreenshot`; full viewport, HUD included) — distinct from the automated `--screenshot=<path>` one-shot. So you climb toward it as a fixed overcast ceiling, pass through it exactly where the whiteout is fully opaque (the ceiling→floor transition is hidden), and it sits as a floor below once you're above the band — the model the user picked after playtesting. The deck's original AABB centre (`_deckCenter`, computed once after it's in the tree) is subtracted so the sheet re-centres on the target. ### GameZ format facts (validated on this install, planes.zbd)

- `nodes.json` `children`/`parent` are **flat list positions**, NOT the `node_index` field (node_index has duplicates).
- Euler `transformation.rotation` composes **R = Ry(y)·Rx(x)·Rz(z)** = Godot's `EulerOrder.Yxz` (fit numerically, zero error, against the 221 nodes that also carry a matrix). When `matrix` is present, use it instead; it is stored transposed — real columns are (a,b,c),(d,e,f),(g,h,i).
- Coordinates are right-handed Y-up with the nose at **-Z** — Godot's frame exactly; no mirroring, no UV V-flip.
- `meshes.json` has `null` entries (empty slots) — keep them to preserve `mesh_index` alignment.
- Polygons are n-gons (3..35 verts): triangulate as fan, or as strip when `flags.triangle_strip`; `normal_indices`/`uv_coords` may be null (272 polys have no normals → flat-shade fallback).
- Materials are `Colored` (RGB 0-255 + alpha) or `Textured` (texture referenced **by name**). Two name quirks: fixed-width 20-char truncation (`blo_fusalagebottom.t` → prefix-match) and mech3ax duplicate renames (`bldhwk_cowling.-12.tif` → strip `.-N` suffix).
- Plane skin pixel data is NOT in planes.zbd — it's in each chapter's `texture.zbd` (C1's contains all player-plane skins).
- Aircraft tree shape: `player_*` → `geometry` → `healthy` → LOD nodes (`nearest` = range.min 0 is highest detail) + `markers` (firepoints/pylons/camera), plus `cockpit1` (separate interior model), `destroyed`, `shadow`, `dontmove` (props: `staticprop1` static; `prop1`/`prop1b`/`prop2*`/`nitroprop1` are spin-animation frames).
- Polygons carry per-corner `vertex_colors` (RGB 0-255, ~30% non-white) = **baked lighting**. The original engine renders world geometry fullbright: texture × vertex color, no dynamic lights. Rendering the world shaded instead comes out murky-dark — use unshaded + vertex colors. Some polys are baked **pure black** on purpose (e.g. the rural road bridge's `rr_bricks03` abutment wedges, `g2` mesh 643) — painted-in shadows, black in the original too; not a bug.
- Polygons carry a signed **draw priority** (v0.6.1 JSON `unk04`; renamed `priority` in current upstream mech3ax — its Polygon struct now reads `flags, priority, zone_set, …`). It layers coplanar geometry: 0 = base surface (terrain, water, fuselage), positive = drawn on top (terrain-transition/crop/forest patches 1, road/rail decals 1–3, baked shadow decals 2–5, plane logos/damage 1–3, cockpit gauge faces 7–8 → needles 8–9 → indicator lights 30 → topmost needle 49), negative = drawn behind (zeppelin interior gasbags −10, sinking-boat hulls −11, skydome walls −49). Ignoring it z-fights every decal against its base; the remake maps it to a per-surface depth bias (see SceneBuilder). Distribution in C1: 12k of 18k polys are 0.
- **Equal priority resolves by draw order, later wins** (validated on C1): within a mesh, polygon list order (tile meshes list base grass before their coplanar `tarmac_road01` roads and `water1_trans*` shoreline blends — all at priority 0); across nodes, flat nodes.json order (apron detail `g140` #4364 over tile `a3` #4043, `someroads` #4865 over `rrtracks_city` #2802, bridge deck #2803 over terrain #2801 — every observed overlay has the higher index). Runway `lite*`/`ltout*` (lights on/off) are coplanar state-variant pairs the engine toggles at runtime, not resolvable by ordering. (An earlier note cited the gyro `tail` mesh's fuselage-skin-then-`agyro_cock1`-lattice order as a within-mesh example — misdiagnosed: those lattice polys are not a coincident overlay but inward-facing single-sided interior structure the original *culls*; see SHOW_BACKFACE below.)
- Polygon flag `unk2` (v0.6.1; upstream `SHOW_BACKFACE`, bit 0) = render double-sided; polygons without it are backface-culled by the original. Winding: the visible side is where the loop runs counter-clockwise (right-handed — Newell normal side; equals Godot's *back* face, hence `cull_front`). Verified on the autogyro: outward deck skin vs inward frame-lattice bulkheads. Honored for aircraft (PlaneBuilder); the world still renders double-sided.
- **Player-plane damage states** (all in the top LOD, per plane): `player_damage_on` = `pdp1`–`pdp8` damage panels (INACTIVE until hit) + `pdp2_h`/`pdp3_h` healthy panels (ACTIVE — real airframe parts); `player_damage_off` = intact duplicates `pdp2i`/`pdp3i` (the damage-detail-OFF variant; exactly one group shows). Initial states come from zrdr anims, not node flags: `player_destruct_reset.json` (`plane_reset`), each plane json's destruct `RESET_STATE` (healthy ACTIVE; destroyed/shadow/staticprop/staticrotor/nitroprop INACTIVE), and `vehicle.json` `destroyable_parts` wires per-part health thresholds to `pdpanelN`/`*_damage_*` anims in `player-1.json`. The `damageindicator` subtree (`nosedamage`/`taildamage`/`*wingdamage`) is the cockpit damage gauge — `OBJECT_CYCLE_TEXTURE` steps its `greenhilite→yellowhilite→orangehilite→redhilite` cycle materials (materials.json `cycle` blocks; frame 0 = pristine = the base `texture` field).
- Node kinds beyond Object3d/Lod: World, Display, Window, Camera, Light. Display has no `name`/`children`; Window/Camera/Light have no `children` — parse tolerantly.

### World structure (chapter gamez.zbd, validated on C1)

- World content lives in TWO places: the `world1` World node's `children` (66 in C1: horizon, cloud groups, zeppelins, trains, fvol volumes…) **and** ~350 top-level parentless subtrees referenced only via the World's `partitions` (12×12 spatial grid over `area` x,z ∈ [-12288, 0]; each cell lists node indices; the union of distinct refs = placed terrain tiles + buildings + vehicles).
- The remaining ~160 parentless roots (bulletholes, firetrails, muzzle flashes, projectiles…) are runtime-spawned effect prototypes — not world scenery — **except the clutter templates** (C1: `terpat02`, `river1`, `river2`), which ARE scenery the engine stamps onto matching-textured terrain at runtime (see `Clutter.cs`; the chapter's `AddClutterTemplates` list in interp.json names them).
- Terrain = ~1 km tiles (`terpat*`/`water1` textures), no transform (verts already in world space), under `Lod` nodes (range 0–2000 = nearest). ### zrdr flight stats (validated on this install)

- zrdr reader files are nested lists; by convention they alternate `key, [values…]` (a "dict"). `vehicle.json` root[0] alternates def-name / property-list with `kind_of` inheritance: `pbloodhawk` → `player_airplane` → `basic_airplane`. Player planes are the `p*` defs (`pbloodhawk` has `nodename player_bhawk`); the non-`p` defs (`bloodhawk`) are AI variants.
- Units are meters/seconds: `fd_speed` 135 m/s ≈ 302 mph matches the Bloodhawk's published top speed; `flight_ceiling` 2500; player.json `nom_gravity` = 20 m/s² (arcade 2 g).
- The `dynamics` block per plane: `pitch/roll/rudder_torque`, `return_rate` (extra centering when stick released), `ang_momentum_damp`, `rec_moments_inertia` (reciprocal, x=pitch/y=yaw/z=roll), `fd_speed`, `drag_factor`, `veh_weight`, `ref_area`. Steady rate = torque·recInertia/damp (Bloodhawk roll ≈ 1.65 rad/s).
- `engines.json` = rows `[id, name, power]`; a plane's `engine` prop picks its stock engine (Bloodhawk: 11 = Lvl-2, 0.62). Engine power scales thrust/acceleration in our model; `fd_speed` stays the level-speed cap.
- Sound (validated): sounds.json `SETS` maps `snd_*` → WAV + flags (`LOOPED`, `3D`, `FREQUENCY` = pitch-shiftable, `RANGE [full-vol, audible]` m, `VOLUME`). Each plane def names its own engine loop (`engine_sound snd_bloodhawkengine` → bloodhawk.wav). player.json curve blocks (all clamped two-point ramps): `engine_sound` = pitch 0.6→1.0 over throttle 0.1→1.0 (volume flat 1.0); `prop_sound` = **overspeed dive whine**, volume 0→0.5 over speed 1.0→1.1× fd_speed, pitch 0.65→1.25 over 1.0→1.2× (WAV not named in readers — we use `snd_enginewhine`, the only pitch-shiftable candidate); `rattle` = snd_planeshake, volume 0→1 over 1.0→1.2× fd_speed.
- All game WAVs are MS ADPCM (fmt tag 2, 4-bit, 22050 Hz, mono or stereo) — Godot only loads PCM/IMA-ADPCM/QOA, hence the decoder in WavFile.cs.
- **Player spawns are per chapter+mission, in the mission's own zrdr** (`extracted/<chapter>/<mission>/zrdr/`, a different archive than the shared top-level zrdr), two schemas (decoded + wired 2026-07-15, spawn positions/headings verified byte-exact against the data for C1/IA1 `zeppelin_run`): (1) **Instant action** — `ia.json` `spawn_points` is a dict scenario → list of `[x, y, z, heading°]`; the original picks one at **random** per launch (e.g. C1/IA1 `zeppelin_run` = 4 spawns, which are the first 4 of `dogfight_ace`). Scenarios seen: `dogfight_ace`, `dogfight_squadron`, `stunt_flying`, `zeppelin_run`. No throttle/speed here — the game uses a fixed start. (2) **Story missions** — `objectives.json` `PLAYER_INIT` = `[1, [x,y,z], [pitch,yaw,roll]°, throttle, speed]` (5 elems, field[0] always 1 across all 50 missions; only the yaw of the rotation varies; `throttle` ∈ {0.5, 0.8, 1.0}; `speed` ∈ {150, 180, 580}). Wired as the spawn **fallback** for M0x missions (position + yaw; verified C3/M01 → `(-1426,150,-1813)@40°` matches the data). Original spawn start (user, confirmed in-game 2026-07-15): **throttle is always 0.5** (across planes), and the plane accelerates from there; **start speed is plane-dependent**. The remake spawns at 0.5 throttle (correct) and a fixed 53.6 m/s ≈ 120 mph **placeholder** kept for now (`FlightController.SpawnThrottle`/`SpawnSpeed`); the plane-dependent start speed is a TODO (candidate: a fixed fraction of `fd_speed` — 53.6/135 ≈ 0.4 for the Bloodhawk — needs multi-plane values to confirm). Note this decouples PLAYER_INIT's `throttle`/`speed` fields from the actual spawn: the spawn throttle is a constant 0.5 while PLAYER_INIT[3] varies per mission (0.5/0.8/1.0), and the spawn speed tracks the *plane* while PLAYER_INIT[4] varies per *mission* (150/180/580) — so fields [3]/[4] are **not** the player's spawn throttle/speed (their real meaning is unidentified). Position + yaw ([1]/[2]) are confirmed correct — C3/M01's spawn matched the original side-by-side.
- **Campaign mission ↔ folder map** (from each `objectives.json`'s `BRF_<REGION>M<n>` objective codes; the prose titles are `MSG_` keys resolved from a string table not in these extracts). The region code + mission number is the campaign's own addressing and does **not** always match the folder's M-number — so `--chapter`/`--mission` for a given campaign mission is: **NW** (Northwest / Sea Haven-night, confirmed) 1→C1C/M01, 2→C1/M02, 3→C1B/M03, 4→C1/M04, 5→C1/M05; **HW** (Hollywood?) 1→C2/M02, 2→C2/M01 *(swapped)*, 3→C2/M03, 4→C2B/M04, 5→C2/M05; **HA** (Hawaii / islands, confirmed) 1–5→C3/M01–M05; **RM** (Rocky Mtn / Colorado?) 1–5→C4/M01–M05; **NY** (New York / Empire State?) 1–4→C5/M01–M04. Region *names* after NW/HA are inferred from the codes. Verified in-game (user, 2026-07-15): HA mission 1 (C3/M01) spawn — position + heading — matches the original side-by-side. So one campaign region ≈ one geographic map, reused across its 4–5 missions (and its day/night/weather variant folders C1/C1B/C1C etc.).
- **Explosions/effects (surveyed 2026-07-14, for the future dogfight milestone): fully data-driven and already extractable — no binary anim format needed.** Three layers, all in zrdr + texture.zbd: (1) *sequencing scripts* — `ai_plane_destruct.json` / `player_plane_destruct.json` are `ANIMATION_DEFINITIONS` readers defining per-plane, surface-sensitive crash sequences (`player_crash_default`/`_dirt`/`_water`; AI equivalents per plane def) that toggle model subtrees (healthy→destroyed), play named sounds at nodes, and `CALL_ANIMATION` into effect scripts; (2) *particle emitters* — `flame_ball.json` (16 `PUFFER_STATE` blocks, e.g. `large_fireball`), `fire.json`, `pufftrails.json`, `flak_trails.json`, `zepskinfire.json` etc. define billboard-particle emitters with full parameters (NUMBER, SIZE_RANGE, LIFETIME_RANGE, GROWTH_FACTOR, random velocity, FRICTION, fade ranges) and a `TEXTURE_SEQUENCE` flipbook with per-frame timestamps; (3) *flipbook textures* in chapter texture.zbd: `fire_f01–06` (fireball), `fire101–112` (sustained fire), `exp_yel01`/`exp_red01`/`exp_blu02`/`exp_gre01` (flash sprites), `fireflare1`. The gamez effect-prototype nodes (`ball_of_fire`, `flak_explosion`, `dense_firetrail`, `explode_here1–9`) are mostly empty anchor Object3d's the emitters attach to. Maps naturally onto Godot GPUParticles3D/billboard quads. (`cam_anim.zbd`/`mis_anim.zbd` remain unsupported but appear unneeded for dogfight effects.)
