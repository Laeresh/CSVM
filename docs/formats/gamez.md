# GameZ format facts

Part of the [format documentation](READoE.md) (see also [world-structure.md](world-structure.md)). Validated against this install with mech3ax v0.6.1; moved from CLAUDE.md on 2026-07-18. Documents formats only — no game asset data (see the repo's hard rule).

> **JSON field names below are mech3ax v0.6.1's.** Since 2026-07-21 this project extracts with the [fork](../plans/PLAN-mech3ax-cs-revival.md) instead, whose JSON is deliberately shape-incompatible — the *format facts* are unchanged, only their spelling. oapping: `{"Object3d": {…}}` → flat node with the variant under `data`; `mesh_index`→`model_index`; `children`→`child_indices`; `transformation`→`transform` (no-transform is the string `"Initial"`; `matrix.a…i`→`original.r00…r22`, plus a `scale`, unit everywhere measured); `meshes.json`→`models.json`; polygon `unk04`→`priority`, `triangle_strip`→`tri_strip`; mesh light `extra`→`vertices`; material `texture` (name) → `texture_index` into `textures.json`, whose entries went `{original, renamed}`→`{name}`; partition cell `nodes[].index`→`values[].node_index`. **One trap:** the fork *also* has a per-node `index` field — 1-based and duplicated, i.e. v0.6.1's `node_index` renamed — which is NOT what `child_indices` point at. The Godot loader reads both shapes; see `GameZ.cs` in [architecture.md](../architecture.md).

## At a glance

This page is the current reference for its documented format family.

## Reference

- `nodes.json` `children`/`parent` are **flat list positions**, NOT the `node_index` field (node_index has duplicates).
- Euler `transformation.rotation` composes **R = Ry(y)·Rx(x)·Rz(z)** = Godot's `EulerOrder.Yxz` (fit numerically, zero error, against the 221 nodes that also carry a matrix). When `matrix` is present, use it instead; it is stored transposed — real columns are (a,b,c),(d,e,f),(g,h,i).
- Coordinates are right-handed Y-up with the nose at **-Z** — Godot's frame exactly; no mirroring, no UV V-flip.
- **Node origins locate nothing reliably.** A node's transform origin is frequently nowhere near its mesh geometry, and many world nodes share a single origin (measured in C1 flight: origin-anchored labels drew 6 distinct labels out of 183 candidate nodes; mesh-AABB-centre anchoring drew 14, on the objects). Anything needing "where the object is" must derive it from mesh vertex data (e.g. the mesh AABB centre), not the node origin. The player planes' `_h` damage panels are the extreme case — identity node transforms with the placement baked into the mesh vertices (see the damage-states bullet below).
- `meshes.json` has `null` entries (empty slots) — keep them to preserve `mesh_index` alignment.
- Polygons are n-gons (3..35 verts): triangulate as fan, or as strip when `flags.triangle_strip`; `normal_indices`/`uv_coords` may be null (272 polys have no normals → flat-shade fallback).
- oaterials are `Colored` (RGB 0-255 + alpha) or `Textured` (texture referenced **by name**). Three name quirks: fixed-width 20-char truncation (`blo_fusalagebottom.t` → prefix-match); mech3ax duplicate renames (`bldhwk_cowling.-12.tif` → strip `.-N` suffix); and (fork extraction only) trailing doubled periods — texture names are stored `prefix\0suffix\0` and decode with a period restored at the first NUL, so a name with an empty suffix comes back as `bldhwk_cowling..tif` for the PNG `bldhwk_cowling.png`. v0.6.1 never exposed the third: it hid those 35 duplicate table entries behind its `.-N` renames; the fork indexes textures by position and never renames, so the doubled name is what reaches a consumer (strip trailing periods before matching).
- Some material texture names resolve to nothing in any texture archive of the install — `pir_spinner` (a pirate-zeppelin spinner disc, referenced by every chapter's gamez) and `barngrill` (C5) are verified absent from the whole extraction. The original engine tolerated missing textures; a consumer must too.
- Every material (`Colored` or `Textured`) carries a `soil` field — the original's numeric surface type id (`crimson.exe` indexes `player_crash_<name>`/`touchdown_<name>` vectors with it on impact), bulk-read from the material record and never fixed up. mech3ax's JSON spells it as a label, but that label is just its own `Soil` enum variant name (a oechWarrior 3 leftover set), not a Crimson Skies name — only seven labels appear over the whole shipped install: `Default`(0)/`Water`(1)/`Fire`(5)/`Grass`(8)/`oech`(11)/`Silt`(12)/`NoSlip`(13) (analysis/surface-classification/FINDINGS.md, 2026-08-11). The other seven Soil variants (`Seafloor`/`Quicksand`/`Lava`/`Dirt`/`oud`/`Concrete`/`Snow`) are valid mech3ax output but carry no material in this install. `GameZ.Parseoaterials` maps the seven observed labels to their id and throws on anything else, since an unseen label means the extractor's enum changed, not that the id is 0.
- Plane skin pixel data is NOT in planes.zbd — it's in each chapter's `texture.zbd` (C1's contains all player-plane skins).
- **A texture's `_1`/`_2` siblings are its hand-authored mip levels, not textures** (decoded 2026-08-02). Every chapter's `texture.zbd` ships 52–91 base textures with a half-resolution `_1` and sometimes a quarter-resolution `_2` (`cblock1`, `cblock1_1`, `cblock1_2`) — **53–103 such levels per chapter, referenced by no gamez material in any chapter** (measured: zero `_N` names appear in any `materials.json`→`textures.json` pair). Dimensions are exactly half/quarter the base in all 542 levels across the install, so a consumer can check the size before believing the name. ⚠ **They are not downsamples and must not be regenerated** — the artists dropped the overall level *and kept the point lights punchy*, so a box filter erases exactly what the level was drawn for: `cblock1_1` keeps 0.385 % of its pixels above luminance 128 where the box filter keeps 0.000 % (mean 4.41 vs 15.63), `cblock1_2` 1.123 % vs 0.000 %, `cblock2_1` 0.354 % vs 0.000 %. The chain is also non-monotone in mean (15.62 → 4.41 → 6.77), which no filter produces. That is the original's "dark with some points, brightening to lit streets" at distance. ⚠ **Registering them as textures in their own right would make them selectable surfaces** — they are levels of the base, and nothing asks for them by name. Instruments: `analysis/item9-depth-bias/mip_census.py` (the shipped data) and `--dump-mips` (the chain the engine installed); `--mips=generated` restores the box filter for an A/B.
- Aircraft tree shape: `player_*` → `geometry` → `healthy` → LOD nodes (`nearest` = range.min 0 is highest detail) + `markers` (firepoints/pylons/camera), plus `cockpit1` (separate interior model), `destroyed`, `shadow`, `dontmove` (props: `staticprop1` static; `prop1`/`prop1b`/`prop2*`/`nitroprop1` are spin-animation frames).
- Control surfaces: every player plane names its movable surfaces uniformly. The deflecting mesh node (`l/r_aileronN`, `l/r_elevatorN`, `l/r_rudderN`, the Fury's `l/r_rudder_rotate`) hangs under a hinge parent group (`lailerN`/`railerN`; `lft_elev`/`rt_elev`/`l_elev`/`r_elev`; `lrudderN`/`rrudderN`; bare `l_rudder`/`r_rudder`; the Peacemaker's `r_rudder1b`) whose transform places and orients the hinge line. Hinge axes corroborated against mesh geometry: ailerons/elevators about local X, rudders about local Y. No zrdr anim/reader defines deflection angles or rates — the original engine drives these procedurally.
- Polygons carry per-corner `vertex_colors` (RGB 0-255, ~30% non-white) = **baked lighting**. The original engine renders world geometry fullbright: texture × vertex color, no dynamic lights. Rendering the world shaded instead comes out murky-dark — use unshaded + vertex colors. Some polys are baked **pure black** on purpose (e.g. the rural road bridge's `rr_bricks03` abutment wedges, `g2` mesh 643) — painted-in shadows, black in the original too; not a bug.
- Polygons carry a signed **draw priority** (v0.6.1 JSON `unk04`; renamed `priority` in current upstream mech3ax — its Polygon struct now reads `flags, priority, zone_set, …`). It layers coplanar geometry: 0 = base surface (terrain, water, fuselage), positive = drawn on top (terrain-transition/crop/forest patches 1, road/rail decals 1–3, baked shadow decals 2–5, plane logos/damage 1–3, cockpit gauge faces 7–8 → needles 8–9 → indicator lights 30 → topmost needle 49), negative = drawn behind (zeppelin interior gasbags −10, sinking-boat hulls −11, skydome walls −49). Ignoring it z-fights every decal against its base; the remake maps it to a per-surface depth bias (see SceneBuilder). Distribution in C1: 12k of 18k polys are 0.
- **Equal priority resolves by draw order, later wins** (validated on C1): within a mesh, polygon list order (tile meshes list base grass before their coplanar `tarmac_road01` roads and `water1_trans*` shoreline blends — all at priority 0); across nodes, flat nodes.json order (apron detail `g140` #4364 over tile `a3` #4043, `someroads` #4865 over `rrtracks_city` #2802, bridge deck #2803 over terrain #2801 — every observed overlay has the higher index). Runway `lite*`/`ltout*` (lights on/off) are coplanar state-variant pairs the engine toggles at runtime, not resolvable by ordering. (An earlier note cited the gyro `tail` mesh's fuselage-skin-then-`agyro_cock1`-lattice order as a within-mesh example — misdiagnosed: those lattice polys are not a coincident overlay but inward-facing single-sided interior structure the original *culls*; see SHOW_BACKFACE below.)
- Polygon flag `unk2` (v0.6.1; upstream `SHOW_BACKFACE`, bit 0) = render double-sided; polygons without it are backface-culled by the original. Winding: the visible side is where the loop runs counter-clockwise (right-handed — Newell normal side; equals Godot's *back* face, hence `cull_front`). Verified on the autogyro: outward deck skin vs inward frame-lattice bulkheads. Honored for aircraft (PlaneBuilder); the world still renders double-sided.
- Polygon flag **`unk3` (raw bit `0x0800`) is `no_clutter`** — ⚠ **corrected 2026-08-10; it was documented here as the OpenFlight `SUBFACE` mark and that name is wrong.** The bit has exactly one writer in `crimson.exe` (`005654f6`), fed from `gg_load.c`'s `strstr(name, "no_clutter")` — it is set from a NODE-NAoE SUBSTRING the artists author, not from an OpenFlight structural attribute. Its one decoded consumer is `FUN_004de2c0`, the clutter walk, which skips a polygon carrying it. **And it does not mean "leave this ground bare"**: where two coplanar layers are painted over each other it selects which one is decorated — C5's flagged ground is dressed by `cblock4/5/6` and its clear ground by `cblock1/2/3/7`, measured at odds ratio 1,037× and confirmed at the controls (`analysis/bl-305-clutter-uv/FINDINGS-layer-pairing.md`, `BL-305`). ⚠ **What survives the rename and what does not.** The *measurements* below stand — they were made on the bit itself and do not depend on its name. The causal story is still open: the remake's `SceneBuilder.NoClutterLayerBias` (renamed 2026-08-10 from `SubfaceBias`, alongside `GameZPolygon.NoClutter` from `.Subface`) layers this bit one priority level up and that empirically works, but "because it is a SUBFACE" is not the reason we can give. The likely account is that the artists name the coplanar overlay layer `no_clutter`, so the two populations coincide without the bit meaning "draw on top" — **this is a lead, not a decode**. Re-confirmed 2026-08-10 (`analysis/item9-depth-bias/cblock_probe8.py`, re-run against current code): disabling the bias at C5's downtown pose puts the wrong, `no_clutter`-excluded ground on top for 78% of the frame, so the bias itself is not redundant with the world's other z-fight mechanisms (`ConflictRankBias`, `SurfaceRankBias`, `NodeOrderBias`) — those never distinguish two coplanar polygons sharing the same node, priority and rank, which is exactly the case here. The world is loaded from `.flt` via `LoadGameGen` (see [interp.md](interp.md)), and **`support\init.gw` applies `GameGenSetSubfacePriorityOffset 1` to it globally, for every mission in the game**, beside `SetCoplanarTolerance 0.10005` / `SetBFETolerance 0.00005` / `SetInverseZTolerance .02`. So a flagged face is layered by **one whole priority level on top of its authored `priority`**, and it is a *second, independent* layering axis — not a value of `priority`. (Whether that offset is keyed off *this* bit is exactly the point left open above.) Serialized `skip_serializing_if bool_false`, i.e. **absent when false**; both mech3ax trees spell it `unk3`. **Containment is exact, never partial** — measured over every C5 flagged polygon, coverage by a coplanar unflagged partner is bimodal (196 at exactly 100%, 251 at ~0% with no partner in the built world, **one** in between); `cblock6` is 100.000% covered by `cblock3`. The textures carrying it are all overlay-shaped: `terpat01/03/04` (**ter**rain **pat**ch), `cliff01-trans1`, `cliff02_trans1`, `river1`/`river3`, `wtr00000`, `pier`, `filmlot5`, and C5's `cblock*` street layer. Per-chapter population: C1 49, C1B **0**, C1C 71, C2 71, C2B 45, C3 1, C4 141, C5 658 (78% of the install). ⚠ **A base/subface pair can look exactly like a day/night or LOD variant set and is not one** — C5's base `cblock4/5/6` are 4× lower-resolution and 3× brighter than the `cblock1/2/3` subfaces laid on them, yet both layers share an identical 256 m UV scale, an identical y-plane and all-white vertex colours (`docs/verification.md` WORLD-1).
- **A polygon's `materials` is a LIST, and the entries past the first are overlay passes** (decoded 2026-08-04, `BL-056`). Each entry is `{material_index, uv_coords}` with **its own UV mapping of the same triangles**, so a pass is not foldable into the base: a C5 fog gradient runs its own 8×64 ramp down a face whose base skin tiles a wall texture. Element 0 is the base skin; later elements draw on top of it, in list order. Install-wide population, all 8 chapters plus planes.zbd: **619 polygons carry a second entry and 7 a third** (C1 385+5, C1B 8, C1C 10, C2 204+2, C2B 8, C3 16, C4 16, C5 352; **planes.zbd carries none** — the "plane logos" of this family are the *world's* zeppelins). Every one of the 626 extra entries ships `uv_coords`, and none repeats its base's `material_index`. What they are, by family: terrain-transition blends over base terrain (`terpat01/02_trans1/2`, `cliff01_trans1/2` — the C1/C2 bulk), C5's fog gradients over water and city (`z3_foggrad` 169, `foggrad8x64` 129, all 142 water ones over `wtr00000`), lit windows (`buildingspotlighted` 34 over `cblock*`), signage (`nypd`, `clock`, `fadedsign01-03`, `buildtrim_subtex01`) and hull logos (`fhunter_logo4` over `piratezepskin2` in every chapter, `cccp_logo1`, `sacredtrust_logo1`, `tarzan_statue`, `tnt`). ⚠ **Every overlay texture in this install carries an alpha channel** (measured on the decoded PNGs: `abld_shadow` a flat 125/255, `z3_foggrad` and `buildtrim_subtex01` ~6 % opaque, `fhunter_logo4` a 49 %-opaque hard cutout) — the pass composites, it does not replace, and a consumer that draws it opaque erases the surface underneath. The remake builds each pass as its own surface with its own depth-bias term (see `SceneBuilder`'s `OverlayPassBias`); reading only element 0 is what dropped the whole feature until 2026-08-04.
- **Player-plane damage states** (all in the top LOD, per plane): `player_damage_on` = `pdp1`–`pdp8` damage panels (INACTIVE until hit) + `pdp2_h`/`pdp3_h` healthy panels (ACTIVE — real airframe parts); `player_damage_off` = intact duplicates `pdp2i`/`pdp3i` (the damage-detail-OFF variant; exactly one group shows). **The `_h` numbering does not reliably name the torn panel at the same spot** (measured across all 11 player planes, mesh-AABB centers): on `player_bhawk`, `player_fbrand` and `player_brigand` it is crossed (firebrand `pdp3_h` = the right-tip skin = torn `pdp1`'s exact footprint, while the left-tip twin of `pdp5` is named `pdp2_h`; bloodhawk `pdp3_h`↔`pdp2`, `pdp2_h`↔`pdp5`); the brigand's two `_h` tip strips have no torn counterpart at all (≥ 1.36 m from any `pdpN`); the balmoral's `pdp3_h` duplicates `pdp2`'s footprint while its `pdp2_h` is a tail-fin panel; the autogyro's `pdp2`/`pdp2_h` sit mirrored ±0.28 m across the centerline. True twins overlap (centers ≤ 0.72 m apart) — **pair by position, never by name** (name pairing was the remake's wrong-wing damage bug, fixed 2026-07-19). Note the `_h` nodes carry identity node transforms with their placement baked into the mesh vertices, so node origins locate nothing — position pairing must use mesh AABBs accumulated relative to the plane root. No zrdr data ever deactivates an `_h` node, yet `plane_reset` re-ACTIVEs them — the engine hides them at damage time by a rule of its own (if that rule is name-based, the original shows the same wrong-wing glitch on these three planes; untested). Initial states come from zrdr anims, not node flags: `player_destruct_reset.json` (`plane_reset`), each plane json's destruct `RESET_STATE` (healthy ACTIVE; destroyed/shadow/staticprop/staticrotor/nitroprop INACTIVE), and `vehicle.json` `destroyable_parts` wires per-part health thresholds to `pdpanelN`/`*_damage_*` anims in `player-1.json`. The `damageindicator` subtree (`nosedamage`/`taildamage`/`*wingdamage`) is the cockpit damage gauge — `OBJECT_CYCLE_TEXTURE` steps its `greenhilite→yellowhilite→orangehilite→redhilite` cycle materials (materials.json `cycle` blocks; frame 0 = pristine = the base `texture` field).
- Node kinds beyond Object3d/Lod: World, Display, Window, Camera, Light. Display has no `name`/`children`; Window/Camera/Light have no `children` — parse tolerantly.
- **`flags.intersect_surface` is the per-node collision-participation flag** (decoded 2026-07-31): false means the original never intersection-tests the node's polygons — neither plane collision nor weapon rays. Surveyed install-wide over mesh-bearing nodes (~19k true / ~2.9k false): every false-flagged name is a non-solid thing — spinning props (`spin`/`counterspin`/`propstill`), wreck/debris pieces (`part*`, `piece*`, `pt*`, `b_part*`, `f_part*`, `zdtop*`), effect geometry (`fire*`, `flake*`, `ripple*`, `splash_polys`, `shadow`, `bflare`, `sflsh`), light glows (`lite*`, `ltout*`, `litebulb`), ropes/reels/sinkers, and the C3 `spiderweb` — while terrain, water, buildings and every destructible healthy variant are true. No false node has a true-flagged mesh descendant anywhere in the install, so the exemption may be inherited subtree-wide. `intersect_bbox` (a bbox pre-test?) is only ever true where `intersect_surface` is also true. Note the reverse direction is not a solidity claim: some effect-ish nodes (`dust`, `burnpl*`, one `splash_polys`) are flagged true.
- **`flags.unk12` (node-flag bit 12, raw `0x1000`) is the GameGen `fluff` keyword: foliage
  clutter, separately cullable** (decoded 2026-08-09, `crimson.exe` via Ghidra). The keyword lives
  in the node-keyword table at `0062c110`, matched by the GameGen record reader `FUN_004c2610`
  beside `clutter`, `facade`, `cfacade`, `landmark`, `terrain`, `can_modify`, `clip_to` and the LOD
  keywords — i.e. the same table whose other entries mech3ax already names, `fluff` being the one
  it left as `unkNN`. Runtime consumer: the per-instance clutter draw `FUN_004d5de0` opens with
  `if (CameraRenderFluffClutter == 0 && (node->flags & 0x1000)) return;`, so fluff is a
  **subclass of ordinary clutter** on the same draw path, not a separate system — it exists so the
  debug switch `CameraRenderFluffClutter` (`0063f5d8` → setter `FUN_004d2110` → `DAT_0062d16c`) can
  drop the greenery while leaving `CameraRenderClutter` (`0063f5f4` → `FUN_004d2100` →
  `DAT_0062d168`) on. Both walk the clutter quadtree `FUN_004d6010` and fade per instance by
  camera distance² scaled by `CameraSetClutterFadeScaleSq` (`DAT_0062d170`). Install-wide census:
  **47 nodes, all in C1, five names** — `firtree1.flt` 13, `bush1.flt` 12, `firtree2.flt` 8,
  `bush2.flt` 7, `dougfirtree1.flt` 7; C1B/C1C/C2/C2B/C3/C4/C5 carry **zero**. The geometry agrees
  with the names rather than merely echoing them: the sample `bush2.flt` has a child bbox of
  3.69 × 6.70 × 3.69 m at `y = 0.0` — a shrub on the ground. ⚠ **"Fluff" is foliage, not cloud.**
  The name and the engine's neighbouring `ZBT_CAoDYN_CLOUDHACK` profiler bucket both invite the
  reading that this is an ambient cloud-puff population (it was chased as exactly that for
  `BL-317`); it is not, and that bucket is the `CLOUD_COVER` whiteout `FUN_0042ee40`
  ([weather.md](weather.md)), not sprites of any kind.
- **oodels also carry `flags.lighting` and `flags.fog`, and both are load-bearing** (decoded 2026-08-02). `lighting: false` = the original turns D3D lighting off for this model, so it draws at full texture x vertex-colour brightness instead of being modulated by the mission's `SUNLIGHT_*` (the remake's `csky_world_light` scalar — see [weather.md](weather.md)); `fog: false` = it is exempt from distance fog. Install-wide over 17,139 models (8 chapters + planes.zbd): **3,003 `lighting: false`** and **225 `fog: false`**, and unfogged is very nearly a subset of unlit (197 of the 225 are both; only 28 models are lit-but-unfogged, 24 of them in C5). Per chapter the unlit population is 155-450 and the unfogged one 21-49. **What carries them is the self-lit art**: every Facade sprite card (the `cloud1`/`cloud2` cloud sprites, lamp/beacon/flare glows, muzzle flashes), the clutter template's tree and bush cards (a camera-facing card has no meaningful normal to light), lit signage and lightpoles, effect geometry (`fire1`/`fire2`, the `splash1`/`bsplsh` water-splash models, `rabbit_blur`), and — in **every** chapter — the **entire `horizon` skydome subtree**, which is 3-6 meshed nodes and is `lighting: false` + `fog: false` throughout. In planes.zbd the unlit set (467 models) is the cockpit instruments, gauges and wing flares; **no plane model is `fog: false` at all**. Honoured since 2026-08-02 (`SceneBuilder`, per-model shader variants) with one deliberate exception: the skydome keeps its fog, because the remake's dome is camera-anchored, 2.5x scaled and ~22 km out rather than the original's, and its fogging is what makes the horizon band grey toward the same wall as the terrain (`WorldBuilder.BuildHorizon`).
- **A node with an empty `parent_indices` AND no World spatial-partition reference is staged
  template-library content, never world-placed geometry** (decoded 2026-08-04, `BL-253`).
  `nodes.json` content lives in exactly two places (see `WorldBuilder`'s own class doc): a node's
  own place in the tree (someone's `child_indices`), or a top-level subtree the World node's own
  spatial-partition grid references directly without it ever being anyone's child. A node in
  NEITHER is built with the game (its mesh/subtree exists) but never actually placed anywhere —
  the game loads it parked at its raw authored transform, inert, and an animation summons it by
  name when it needs one. Census (C2): **166 nodes** meet this test. Beyond the handful of engine
  roots (`world1`, `display`, `camera1`, `window1`/`sgwin`, `spyglass`, `sunlight`, `letterbox` —
  none of them `Object3d`, the only `Kind` this applies to), that set IS the template library:
  every effect template (`lg_fireball`, `flame_ball_01`–`_03`, firetrails, splashes), every
  weapon/projectile model (`he_rocket`, `muzzle_burst`/`muzzle_burst2`), zeppelin wreck templates
  (`*_destroyed.flt`), clutter templates (`filmblock*`/`resblock*`), cutscene props — and both
  `CALL_ANIoATION` template roots `BL-253` diagnosed (`facdsticks`, `genx12`). Two corroborating,
  non-load-bearing bits travel with the same set: `zone_id == -1` (a world-placed node instead
  carries a real zone, 0+) and the Object3d variant's own `signs == 128` (a placed node carries
  `signs == 4108`). 164 of the 166 are `active: true`; the two `active: false` ones
  (`letterbox`, `sunlight`) are the data's own opt-out and are never summoned. Engine-side:
  `GameZ.IsLibraryRoot`.
  - **Several of these templates ship as N pre-built, same-shape sibling records instead of one —
    the data's OWN pooling, not a runtime invention.** Verified by comparing sibling node records
    (matching `flags`, `zone_id`, `parent_indices: []`, and — checked on `flame_ball_01`/`_02` and
    `muzzle_burst`/`muzzle_burst2` — an identical one-child subtree shape differing only in which
    mesh/model index the child carries): `sonic_ring`/`sonic_flare` ×5, `mb1`/`mb_spinflame` ×5,
    `zep_skin_fire1`–`4`, `yellow_spark_01`/`_02`, `flame_ball_01`–`_03`, `fire_here`/`fire_here2`,
    `muzzle_burst`/`muzzle_burst2`. Where a template ships this way, N *is* the original's own
    concurrency answer for it — read off the census, never re-invented as a config number.
    `facdsticks` and `genx12` are the opposite case: each ships as **exactly one** record, so
    their own concurrency (if any — `facdsticks`' original A/B shows several call sites' copies
    running in parallel, `BL-253`'s CAP-24) cannot be read from the data at all and is a `TUNE`
    entry (`CSVo/data/effect_pools.json`'s `localCallRoots`, `backlog.md`'s `BL-231` list) like
    every other pool size this engine invents.
- **`zone_id`'s runtime meaning, decompiled (2026-08-09, `crimson.exe` via Ghidra,
  `PLAN-weather-decompile-match` A1).** `FUN_0056c430(node_zone_id)` is the per-node visibility
  gate: a node draws iff its `zone_id` is `−1` (always visible — the library-root/world-placed
  sense noted above still holds), or `zone_id` is in the camera's currently-armed zone set. That
  set is armed every frame by `FUN_0042ee40` via `FUN_004d62d0` with `{count=2, 0, state}`,
  `state` being the camera's current weather zone (1/2/3, [see weather.md](weather.md)'s
  zone-state decode) — so the gate is a **per-frame camera-state filter**, not a static
  per-mission partition. oission content authored `zone_id 1` and world content authored
  `zone_id 2` (a chapter's cloud deck, its `cloudparent` facades, its `fvol*` volumes) both live
