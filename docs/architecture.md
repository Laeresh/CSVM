# Godot project — per-module implementation notes

Deep implementation notes for `CrimsonSkies/src`, moved from CLAUDE.md on 2026-07-18: what each module does, why the implementation is the way it is, verified diagnoses, TUNE constants, and dead ends not worth re-chasing. **Read a module's bullet before modifying it, and update the bullet in the same turn as a code change.** The compact module index, build/run commands, and CLI flags reference live in CLAUDE.md.

- `src/Mech3/GameZ.cs` — loads a mech3ax GameZ extraction (ZIP or unpacked dir): nodes / models / materials / textures JSON into plain C# objects. **Reads two extraction shapes (2026-07-21, revival-plan item 13):** the pinned v0.6.1 binary's ("legacy") and the fork's ("unified"). They carry semantically identical data — verified field-for-field on C1 + planes before the port was written: same node count and order (7064), same `model_index` values, same names (bar the Display node, unnamed in legacy and `"display"` in unified), the `"Initial"`↔null transform correspondence exact at 3675/3675, same partition refs (346/346) — but spell it differently: `{"Object3d": {…}}` → a flat node with the variant under `data`; `mesh_index`→`model_index`, `children`→`child_indices`, `transformation`→`transform` (the no-transform case is the string `"Initial"`, and the stored matrix moved from `matrix.a…i` to `original.r00…r22`, appending the translation as `r30…r32` which duplicates `translate` and is not read); `meshes.json`→`models.json` with polygon `unk04`→`priority` and `triangle_strip`→`tri_strip` and mesh light `extra`→`vertices`; materials carry a `texture_index` into `textures.json` (itself `{original, renamed}`→`{name}`) instead of an inline `texture` name, so textures.json is now parsed and must be read **before** materials; partition cells `nodes[].index`→`values[].node_index` (the unified shape's sibling `node_indices` array is empty in every chapter but is read anyway). **Two traps worth not re-discovering.** (1) The unified shape exposes a per-node `index` field that is 1-based and contains duplicates — it is legacy's `node_index` renamed, NOT a list position. `child_indices` are flat list positions exactly as `children` were; this was settled by counting parent/child agreement under both interpretations (6553 as positions vs 59 as index values) *before* writing the parser, because getting it backwards rebuilds the scene graph wrong without erroring. `GameZNode.Index` therefore stays the enumeration counter, never the JSON `index`. (2) Unified transforms carry a `scale`, which legacy had no concept of; it is unit on all 4181 transformed nodes of C1 + planes, so it is deliberately ignored rather than plumbed through. Reading both shapes (rather than cutting only to the new one) is what makes the v0.6.1 rollback a data-only operation — `ExtractAssets.ps1 -Unzbd <v0.6.1 unzbd>`, no code revert — and it let the port be proven by rendering the same scene from both trees to an md5 match. Parses World partition refs, per-corner vertex colors, per-mesh `lights` arrays (point-sprite lights: the night sky's stars, nav/tower beacons), and the per-polygon **draw priority** (v0.6.1 JSON key `unk04`; upstream mech3ax has since renamed it `priority` — both keys accepted). Each GameZNode records its flat `Index` in nodes.json (= the original's draw order, used as the cross-node layering tie-break). For the **World** node it also parses the map's `area` ground-plane bounds (`{left=xMin, right=xMax, top=zMin, bottom=zMax}` in Godot world coords → `HasArea`/`AreaLeft/Top/Right/Bottom`) and the partition grid dimensions (`PartitionCols`/`PartitionRows`) — WorldBuilder's map-edge continuation uses these to size and place the mirrored border terrain. `WorldTransformOf(node)` accumulates a node's world transform up its parent chain (parent is a flat list position, so a lazily-built child→parent map inverts the children lists); used to resolve objective-marker world positions (the stunt `dzN` points) without building the skipped marker nodes into the scene — most sit directly under the identity World root anyway, so the raw translation is already world-space.
- `src/Mech3/TextureArchive.cs` — texture lookup over an unzbd texture ZIP **or an unpacked directory** of those PNGs, handles the name quirks below. **Third quirk added 2026-07-21 (revival-plan item 13): a trailing doubled period.** Texture names are stored `prefix\0suffix\0` and decode with a period restored at the *first* zero, so a name whose suffix is empty comes back doubled — `bldhwk_cowling..tif`, whose PNG is plain `bldhwk_cowling.png`. v0.6.1 never exposed this: it hid those 35 duplicate table entries behind `.-N` renames, which the existing regex already undid. The fork indexes textures by position and never renames, so the true doubled name reached `Resolve` and matched nothing (neither exact nor prefix — `bldhwk_cowling` does not start with `bldhwk_cowling.`). Fixed with a `TrimEnd('.')` retry. The `.-N` branch is now legacy-tree-only but kept, since the loaders read either tree. Exposes `LastHadAlpha` and `LastAlphaIsSoft` — the latter classifies the alpha channel from the pixels: "soft" means a 0.5-threshold scissor cutout would erase the texture or shred it (max alpha < ~140/255, or partial alpha dominating with few near-opaque texels). True for the original's translucent overlays: baked shadow decals (`bldgshadow`/`abld_shadow`/`lkshad*` peak at ~125/255 — fully invisible under scissor; `thin_shadow` at 155 became solid-black wedges), clouds, prop blur, waterfalls, smoke. **Missing-texture logging (Run-2 item 1):** each unresolved name is reported **once** (a `_reportedMissing` HashSet) as a plain `GD.Print` line — never `GD.PushWarning`, which in Godot .NET prints a full managed stack trace per call and buries real errors; `MissingTextures` exposes the deduped set for PlaneViewer's one-line end-of-build summary. A static `KnownAbsentFromGameData` set (`pir_spinner` — a pirate-zeppelin spinner disc referenced by every chapter's gamez; `barngrill` — C5; both verified absent from the whole extraction, so the original engine tolerated them too) is surfaced via `IsKnownAbsent`: SceneBuilder renders those as neutral gray (0.5) instead of the debug **magenta**, which now flags only genuine name-resolution failures (our bug), not data gaps.
- `src/Mech3/SceneBuilder.cs` — shared GameZ-subtree → Node3D/MeshInstance3D builder: n-gon triangulation, material+mesh caches, keeps only nearest LOD, takes a skip predicate. **Draw-order replication → depth bias (the z-fighting fix):** the original layers coplanar geometry by (1) per-polygon priority, then (2) draw order — polygon list order within a mesh, node order across meshes (nodes.json is a DFS serialization = draw order; later wins under DX7 LESSEQUAL). All three are mapped to a scale-invariant polygon offset: every non-billboard surface uses a generated ShaderMaterial whose vertex shader scales the view-space position toward the eye by `depth_bias + node_bias` — identical projected position, nearer depth. Meshes are split into one surface per (material, priority) in first-occurrence order; `depth_bias` = priority × `DepthBiasPerLevel` (2e-4, TUNE) + surfaceRank × `SurfaceRankBias` (2e-6, capped at rank 5 — the within-mesh tie-break: gyro canopy lattice over fuselage skin, tile roads over tile grass); `node_bias` (an `instance uniform`, set per MeshInstance3D — needs Forward+) = GameZNode.Index × `NodeOrderBias` (5e-8 — the cross-node tie-break: airfield apron detail over base tile, road decals over rail decals). **Instance-uniform buffer (Run-2 item 2):** Godot allocates 16 vec4 slots per instance carrying any instance uniform, so the default 65536-slot global-shader-variable buffer caps at ~4096 mesh instances — C4 (4234) and C5 (4746) overflowed it, flooding "Too many instances" errors *and silently dropping `node_bias`* on the overflow (decals z-fight again). `project.godot` now sets `rendering/limits/global_shader_variables/buffer_size=262144` (~16384 instance slots, a 4 MB GPU buffer); C1 (3481) always fit. Negative priorities push away (skydome −49, zeppelin gasbags −10, pilot body −1). The shader mirrors StandardMaterial3D's look (vertex-color × texture albedo sampled `filter_linear_mipmap_anisotropic` — 16× via `project.godot`'s `textures/default_filters/anisotropic_filtering_level=4`, the Run-2 item-2 fix for grazing-angle ground blur; cull disabled, unshaded when fullbright, Burley/GGX + roughness 0.85/metallic 0/specular 0.5 when shaded; opaque/scissor/blend fragment variants) and is cached per feature combo; materials cache per (material, priority, cappedRank). **Billboard (cloud-sprite) materials** are a separate `ShaderMaterial` (`GetBillboardShader`, cached per blend/scissor in `_billboardShaderCache`): the same hand-rolled keep-scale billboard as CloudPuffs (`MODELVIEW_MATRIX` rebuilt from `INV_VIEW_MATRIX` columns + `MODEL_MATRIX[3]`), `COLOR × albedo`, `blend_mix`/`depth_draw_never` for the soft-alpha clouds — **no depth bias** (free-floating sprites have nothing coplanar to fight) but **carrying the same cylindrical fog term** as the world shader, so distant sprites fade into the fog wall instead of punching through as crisp white (Run-2 item 4). It declares **no** `csky_fog_on` instance uniform (clouds always fog, and omitting it keeps the sprites off the instance-uniform buffer — see item 2). This replaced the old fog-immune `StandardMaterial3D` billboard. **Sidedness:** `cullBackfaces: true` (used by PlaneBuilder) additionally splits surfaces by the per-polygon SHOW_BACKFACE flag (`unk2` in v0.6.1) and backface-culls the single-sided ones — `cull_front`, because the source's visible side is where the vertex loop runs counter-clockwise (right-handed) while Godot front faces are clockwise. This is what hides the autogyro's inward-facing interior frame lattice (`agyro_cock1` bulkheads in the `tail` mesh) so its aft fuselage shows yellow skin with openings, like the original. No plane node has a mirrored (negative-determinant) transform, so the blanket cull direction is safe. The world builder still renders everything double-sided (cull-disable) — switching it to per-polygon culling is a candidate cleanup, unvalidated. Known accepted limit: the tie-break hierarchy is approximate for extreme node-index spans (a prio-0 node >~4000 indices later can out-bias a prio-1 overlay; no such pair observed in C1), and cross-node deltas of ±2 indices sit at interpolation-noise level (one 6-poly rail/transition patch NE of the C1 bridges). **Alpha handling:** textures whose alpha is "soft" (see TextureArchive.LastAlphaIsSoft) alpha-blend automatically — this is what renders the baked shadow decals correctly (they were invisible or solid black under scissor) — in addition to the caller's explicit `blendTexture` predicate; other alpha textures scissor (hard cutout — fences, trees, railings). `fullbright: true` renders unshaded (texture × baked vertex color — the original engine's world look). `generateCollision: true` attaches a static trimesh collider (`StaticBody3D` + `ConcavePolygonShape3D`, cached per mesh, `BackfaceCollision = true` because the source winding is inconsistent) to each mesh; a `collisionSkip` predicate exempts subtrees (renders but not solid). The explicit `blendTexture(name)` predicate still promotes chosen alpha textures to `Alpha` blending on top of the automatic soft-alpha rule (WorldBuilder passes it for the clouds, PlaneBuilder for the `*blur*` discs — both are also caught by the classifier, so the predicates are now belt-and-braces). Only consulted for textures that actually carry alpha, so opaque cloud/sky (`cloudlayer`/`sky*`) is unaffected. A second optional predicate `billboardTexture(name)` renders the matching meshes as camera-facing billboards (the cloud *sprites* — flat 2D cards in the source): the material gets `BillboardMode.Enabled` and the mesh is recentered on its own quad centroid (offset stored per mesh, re-applied as each instance's local position) so the billboard pivots at the quad center, not the node origin — the source sprite quads sit up to ~650 units off their origin, so without recentering they would swing around as the camera turns. Recentering also tightens transparent sorting (each sprite sorts by its true center). Meshes with `lights` additionally get a POINTS-primitive instance rendered by a dedicated point-sprite shader (reworked 2026-07-18 on user feedback — the original's lamps are camera-oriented soft glow sprites, star-like and clearly brighter than the old fixed 3 px dots): additive soft radial glow (gaussian core, no hard cutoff, ×1.6 gain TUNE), distance-sized from a ~6 m world diameter (TUNE) clamped to [3 px, `MaxSizePx`]; per-light **decoded** params drive it — light `unk08` = size scale (0 default / 1 / 2 / 5 = the lighthouse), `unk64` = max sprite px (30), `unk68`/`unk52` = visibility range in metres (1500/2500/4000), the range applied as a smoothstep distance fade which also stops in-map beacons punching through the fog from kilometres outside (the old item-7 nit). One POINTS surface per (size, range) group per mesh, materials cached per param set; an `instance uniform csky_light_fade` opts the camera-anchored skydome's stars out of the range fade (they sit ~22 km out; `WorldBuilder.DisableLightRangeFade`) — verified: harbor lamps/blue pier lights/lighthouse render as bright soft glows, stars + moon intact above the deck, `--fly` clean. Never collidable/shadowed; black effect-prototype lights add nothing and stay invisible. **Glow flare sprites (same day, the user's real complaint):** the visible lamps are not mesh-lights but **single-quad flare MESHES** (`refinery_flare` 16 m + `gen_flare_yellow` 4 m on `oil_liteflare.tif`, `docklight_flare` 9.6 m blue on `dock_liteflare.tif`, lighthouse `litehsflare` 19.2 m on `poleflare.tif` — full soft-alpha ramps on black) that the original camera-billboards; world-fixed they render edge-on/skewed (the user's crop: a squashed quad with the texture's ray tips at its corners). A `glowTexture` predicate (WorldBuilder passes `IsFlareTexture` = name contains "flare") routes them to the billboard shader with a `glow` variant bit: always alpha-blend (scissor would cut the soft ramp into a hard star), fog term kept, **no `csky_world_light` night dim** (a lamp is a light source). **Scoped per-MESH via `IsGlowSpriteMesh` — single-polygon all-flare meshes ONLY** (and the collision exemption mirrors it): the C1-C5 scan found the same flare textures on polys INSIDE regular geometry (C4 world Brigand wing meshes carry an `oil_liteflare` poly; the shared 76-poly effects-atlas mesh has flare polys) where whole-mesh recenter/billboard would distort the geometry, and 6-poly `flare_green` STRINGS 22–72 m long that would swing around a common centroid — both keep static rendering (per-poly billboard pivots are the faithful upgrade, backlog). Verified: refinery lamps/pier lights render as camera-facing star sprites matching the user's original-game crop; C1 colliders 2670→2566 (flare quads no longer solid); C1/C4/C5 fly-smokes clean. **Distance fog:** the original's fog volume is a vertical **cylinder** around the camera, not a sphere (user-diagnosed 2026-07-17): the generated shader mixes ALBEDO toward the fog color by **horizontal** (x/z) camera distance, scaled by an altitude fade — full fog below `FOG_ALTITUDE`[0], none above [1] — so the overcast deck/sky overhead stays clear instead of graying out (zone1's altitudes 970→1047 = exactly cloud-band bottom → whiteout-band centre; zone2's 4000→5000 > flight ceiling = night fog at every flyable altitude). Implemented per-fragment: `INV_VIEW_MATRIX` lifts the view-space VERTEX back to world space for `distance(world.xz, CAMERA_POSITION_WORLD.xz)` and the fragment-altitude fade. Driven by three **global** shader params `csky_fog_color`/`csky_fog_range` (near/far)/`csky_fog_alt` (full-below/none-above) that PlaneViewer registers + sets once per flight from weather.json (no-op range when not flying, so static viewing is unfogged), plus a per-instance `csky_fog_on` (default 1) so the caller can opt a subtree out — WorldBuilder sets it 0 on the camera-anchored skydome, whose below-horizon skirt would otherwise fog solid gray at ~22 km. The aircraft shares the term but is a no-op at chase distance (always within the near range). **Fullbright world brightness (Run-2 item 6, 2026-07-18):** two coupled fidelity fixes on the `!shaded` branch only (shaded/plane surfaces keep raw COLOR + full brightness). (1) **Gamma-space vertex modulate** — the original is a DX7 fixed-function engine whose `D3DTOP_MODULATE` multiplied texture × baked vertex colour in *gamma* (sRGB) space; we render in linear space, so our `linear_texture × COLOR` came out too bright/desaturated wherever the baked colour is < 1 (baked shadow/AO — 30% of the C1 world's corners, min 0). The fragment now linearises COLOR before the multiply (`csky_srgb_to_linear`, the shared `SrgbToLinearFn` const, Godot's exact sRGB EOTF), reproducing the gamma-space product — fixes the terrain's washed-yellow → saturated-green (measured greenness G−R +3.6 → +16.9 vs the original's +18…+23). (2) **SUNLIGHT dimming** — a global `csky_world_light` scalar (default 1.0, declared only when `!shaded`) multiplies ALBEDO **before** the fog mix (so FOG_COLOR is unaffected); PlaneViewer sets it per-flight from `WeatherState.WorldLight` (the mission's SUNLIGHT), fed already-linearised so this linear-space multiply lands the dimming in gamma space too (a raw linear ×0.80 only reaches 210→190; gamma-space lands the deck 210→169, matching the reference). Together: deck/sky 168 vs 169, terrain mean 59 vs ~57, fog 170 vs 176. The same two fixes are duplicated in the cloud-billboard shader and Clutter's tree shader (all three emulate the original's unshaded world pass); the cloud deck (`cloudlayer`, 100% white vertex colours) is unchanged by the modulate and rides only the SUNLIGHT dim. **Texture substitution (2026-07-20):** an optional `textureSubstitute(name, resolved)` hook every material's texture passes through — how `PlanePainter` swaps in a recoloured skin or a decal per aircraft. `_textures.Find()` still runs even when a substitute exists, because it is what sets `LastHadAlpha`/`LastAlphaIsSoft` that the blend-vs-scissor choice reads; a substitute must therefore keep the original's alpha class (the decal placeholder and the decal are both `alpha=Full`, so that swap is alpha-neutral by construction). **Aircraft normal sign (2026-07-20):** the `shaded` branch emits `NORMAL = -normalize(MODELVIEW_NORMAL_MATRIX * NORMAL)`. The minus is not cosmetic and must not be "simplified" away. Our source normals point to the polygon's visible side, and that side is the CCW loop = Godot's BACK face (the reason single-sided surfaces use `cull_front` above) — so every visible aircraft fragment is back-facing, and Godot negates `NORMAL` on back faces. The normal therefore reached the light calculation pointing *into* the airframe and every upward surface shaded as if lit from underneath. Pre-negating cancels the engine flip and is correct for both sidedness cases: single-sided shows only the CCW side, and a double-sided (`cull_disabled`) polygon gets the engine's flip on exactly the side that needs it. The file data was ruled out first — 0 of 1827 Fury triangles disagree with their winding (triangulated the way the renderer does: fan vs alternating strip; a Newell normal over a *strip's* raw index list is meaningless and produced a false 7–14% inversion rate on the first pass), no aircraft node has a mirrored transform, and there is no `GenerateNormals`/`Index` weld. Fullbright emits `""` for the sign and its shader text is byte-identical to before, so the world is provably unaffected. Measured on the Fury (mesh lab, ambient off, sun straight down, from above): wing top 6.4 → 73.8.
- `src/Mech3/PlaneBuilder.cs` — thin wrapper: builds one aircraft, skips cockpit/destroyed/shadow subtrees, plus every plane's `*_hook` skyhook subtree (`blood_hook`, `kest_hook`, `gyro_hook`, … — retracted by default: each `*_hook.json` anim's RESET_STATE deactivates the group + its arm/door nodes; `player_hook.json`'s `player_extend_hook` extends it only for zeppelin docking). Shaded (dynamic lighting). Builds its SceneBuilder with `cullBackfaces: true` (see SceneBuilder — aircraft interior structure must be backface-culled or it paints over the skin). **Damage panels (fixed 2026-07-16):** every player plane's top LOD has a `player_damage_on` group holding `pdp1`–`pdp8` (damage-state panels, `damage1/2.tif` torn-skin textures — start INACTIVE per `player_destruct_reset.json`'s `plane_reset` anim) *and* `pdp2_h`/`pdp3_h` (the matching HEALTHY panels, ACTIVE at reset — real airframe sections: the Bloodhawk's wingtips, the Kestrel's outer wing thirds with the roundels). PlaneBuilder skips `pdpN`/`pcdpN` (digits-only suffix) but renders `pdpN_h`; the sibling `player_damage_off` group (intact duplicates `pdp2i`/`pdp3i`, the original's vehicle-damage-detail-OFF variant) is skipped wholesale. The old code skipped `player_damage_on` entirely, which amputated the `_h` panels (Bloodhawk flew without wingtips, Kestrel without outer wings). Propellers are handled via `PropParts` (below): the default exterior build keeps the still `staticpropN`/`staticrotorN` disc and hides the blur layers; the `spinningProps: true` build (free flight) does the reverse — hides the static disc, keeps the `propN`/`propNb` (+ autogyro `rotorN`/`rotorNb`) blur layers for a `PropAnimator` to spin (`nitropropN` stays hidden either way — no nitro system yet; hiding it in flight is also load-bearing visually — it is a NON-spinning blur disc, so leaving it in overlays a fixed disc on the spinning ones whose edge paints a 1px seam that shimmers as the camera moves). It also passes SceneBuilder a `blendTexture` rule for the blur textures (`*blur*` → `rotorblur`/`zeprotorblur`): those discs are soft sprites whose alpha peaks at ~26%, so the default 1-bit AlphaScissor cutout erased them entirely (looked like a missing/frozen prop) — alpha-blending them (as with the clouds) restores the translucent spinning-disc, clearly visible against bright sky and subtly over dark terrain, as in the original. **Wing-light flares (2026-07-16):** after building, `Build` collects each plane's `wing_flare1`/`wing_flare2` wingtip sprite quads (see `WingLights`), builds them **hidden** (the original's `wing_light.json` RESET_STATE starts them off), and re-skins each glow quad (`oil_liteflare.tif`) with a shared additive, camera-facing **billboard** material tinted the data's warm amber (LIGHT_STATE COLOR 0.88/0.78/0.36) — the source quads are one-sided, so previously the flare only showed from behind. The collected nodes are exposed as `WingFlares` for a `WingLightBlinker` (flight only) to flash; the static viewer leaves them off. Only planes with the nodes get flares — the Bloodhawk and autogyro have none in the data. **Run-2 item 10c/d:** flight builds — and static builds passing the `damagePanels: true` ctor flag (the viewer's `--damage` lab; `_withDamagePanels = spinningProps || damagePanels`) — construct the exterior `pdpN` torn-skin panels **hidden** instead of skipping them (the plain static viewer still skips; `pcdpN` cockpit panels always skipped) and collect them + their `pdpN_h` healthy twins as `DamagePanels` for `DamageVisuals` to flip; `BuildDestroyed(rootName)` builds the plane's `destroyed` wreck-piece subtree (skipped by `Build`) with the accumulated plane-root→destroyed transform chain baked into the returned root — `CrashBreakup` scatters its children on a crash. **Live repaint (2026-07-20):** `Repaint(scheme)` swaps an already-built aircraft's livery without rebuilding it — a fresh `PlanePainter`, then `SceneBuilder.Repaint()` re-resolves every material in that builder's `TexturedMaterials` registry (material → source texture name, recorded at build) and writes the result back into the live `ShaderMaterial`'s `albedo_tex`. Repainting an aircraft's ~8 small skins is a few ms where a model rebuild is ~38 ms plus the mesh work, which is the difference between an interactive slider drag and a slideshow. `Repaint(null)` hands back the archive's own textures, so "unpainted" is exactly the pre-paint state, not an approximation of it. The skin prefix is cached from the first `Build` (`SkinPrefix`), since that is what discovers it.
- `src/Mech3/PaintScheme.cs` — one aircraft livery (2026-07-20): pattern name + three colours + three decal indices, the `paint_*` record a vehicle.json def carries (`ace_*` in a mission ia.json, binary in a saved `.pln` — see `docs/formats/paint.md`). Colour triples here are **always integer 0–255**, never weather.json's dual float/int encoding, so no `>1` test. `LoadCatalog(zrdr)` walks vehicle.json's alternating name/props root and keeps one scheme per pattern name — the `_2`/`_3`/`_5` per-chapter roster duplicates repeat their base def verbatim, and `player_fortune` (on `devastator`/`wingman`) ships a pattern name with **no colours at all** because they live engine-side, so its catalog entry is filled with the Fortune Hunters red `223,0,41` the original's paint UI shows and the value read out of a saved `.pln` at 0x68. `Random()` is deliberately NOT three independent RGBs (that gives clown planes): it follows the shape all twelve shipped schemes share — slot 1 an identity colour (half the time an actual catalog squadron colour, else a fresh hue held to the band those colours occupy), slots 2/3 a dark and a light trim that are mostly neutrals, with catalog trims and the occasional muted tint mixed in so `cccp`'s red-and-yellow stays reachable. Decal ranges match how every shipped def uses the slots: nose from 21–49 (nose art), tail/wing from 00–20 (squadron logos). **Gotcha:** index the catalog with `RandiRange`, never `(int)Randi() % n` — `Randi()` returns a full uint and the cast overflows negative for half the range, which threw `ArgumentOutOfRangeException` on the first 2P flight.
- `src/Mech3/PatternLibrary.cs` — the original's paint patterns and the `.BM` reader (2026-07-20). Scans `extracted/rof/ASSETS/GRAPHICS/<PATTERN>/` (produced by `ExtractRof.ps1`; container + texture format in `docs/formats/rof.md`). `PaintBitmap.Load` reads one `.BM`: **u16 height then u16 width** (that order, not the obvious one — settled upstream against the game's own textures), then `w*h*10` bytes of planes — 3n interleaved RGB shading, then three separate n-byte per-slot weight masks, then 4n overlay. `HasOverlay` is precomputed so the common empty-overlay case costs nothing per texel. **A pattern is per aircraft**, which is the whole reason this class has a `PatternsFor(prefix)`: `FORTUNE` covers all eleven planes, every other pattern one to three, and the Fury's four (FORTUNE/BLCKSWAN/HUGHES/STUDIO) match the user's four Fury reference screenshots exactly — that correspondence is what confirms this list *is* what the original's paint UI offers. `Skin()` caches per (pattern, skin) so several aircraft in one session share a decode. A missing extraction is not an error: `Load` returns an empty library plus one line naming `ExtractRof.ps1`, and everything downstream builds unpainted.
- `src/Mech3/PlanePainter.cs` — applies a scheme to one aircraft (2026-07-20): paints its skins from the pattern's region masks, swaps the three decal placeholders. **Read `docs/formats/paint.md` and `rof.md` before touching this.** The composite is the original's, per texel: `shading * (w1*c1 + w2*c2 + w3*c3) / 255`, then the overlay alpha-over. Two things that are easy to get wrong and are load-bearing: the shading map is the **`.BM`'s own base plane, not the ZBD skin of the same name** (they are different images — the ZBD one is the blue-gray key texture, the `.BM` one neutral), and the ZBD skin's **alpha** is copied onto the composite where the two agree on dimensions, because `SceneBuilder` already chose blend-vs-scissor from that texture's alpha class before the substitution happens. Parts a pattern ships no `.BM` for return null and keep their ZBD texture — normal, since a pattern covers airframe skins, not spinners or cockpits. `PrefixFor` reads the skin prefix off the model's own `*_noselogo`/`*_taillogo`/`*_winglogo` materials — **any of the three**, the Firebrand ships no `fir_noselogo`. Built per plane instance and it **never mutates the shared `TextureArchive` cache**. *History worth keeping:* this replaced a hand-authored per-aircraft table of hue windows, written when the region table was believed absent from the game data. That version worked (a correct red Bloodhawk, twelve distinguishable liveries) but structurally could not express a region with no hue, could not paint the Fury at all, had to guess slot order from region area, and needed a soft hue/saturation falloff purely to stop antialiased borders speckling. All four problems are properties of inferring regions from colour, and all four vanished with the real masks — which also turned out faster, a flat multiply-add per texel against per-texel HSV plus a percentile pass.
- `src/Mech3/PropParts.cs` — classifies a plane's propeller/rotor subnodes by name (`staticpropN`/`staticrotorN`, `nitropropN`, `propN`/`propNb`, `rotorN`/`rotorNb`) and gives each spinning kind its local spin axis + rate. - `src/Flight/HudMetrics.cs` — **the one place the flight HUD decides how big it draws** (M2.5 item 6). Every element (compass tape, gauges, marker, scoreboard, the text block) is calibrated against a 1440p reference (`OriginalScreenshots/HUD.png`) and used to scale by a plain `viewportHeight/1440`; inside a SubViewport pane that is the *pane* height, so a quarter-height 4P pane drew the dials at quarter size while still being half the screen wide — unreadable dots in empty space. The rule here splits the two factors: the **window** height sets the base scale (a 4K screen still gets a big HUD, a 720p one a small one, exactly as before) and the pane's share of it is damped through a square root — `PaneFactor` = `sqrt(paneH/windowH)`, so a 2P pane draws at ~71 % and a 4P pane at 50 % instead of 50 %/25 % (the damping exponent is TUNE; console splitscreen does the same thing for the same reason). What is **not** tunable is the single-player identity: with one full-screen view the pane fraction is exactly 1, `PaneFactor` is 1, and `Scale` returns the old `viewportHeight/reference` unchanged — that is what made the 1P regression provable (4 of 230,400 sampled pixels differ from the committed baseline in a `--fly` shot, none in the HUD bands, against a 13,346-pixel run-to-run noise floor) rather than merely hoped for. **Gotcha it introduces:** damped sizes only stay on screen if positions are anchored to a pane *edge* — see GaugeCluster's bottom-anchored dials and FlightController's two-line text block.

Documented in `docs/formats/weather.md`. weather.json is one alternating dict, but the `CLOUD_COVER`/`WIND` blocks pair keys with **bare scalars** (`"TOP", 1124`) not lists, so `ZrdrDict.FromAlternating` (which needs list values) can't read them — they're walked as raw key/next-element pairs; the per-zone blocks are all list-valued and go through the normal dict. `Fog(zone)` returns the zone's fog (a no-op fog if absent — near/far so far out nothing fades); `WhiteoutAmount(altitude)` is the 0..1 overlay opacity — a symmetric trapezoid (user-observed in-game): clear sight (0) at BOTTOM and TOP, ramping linearly to a fully-opaque core (1 — the plane vanishes) that is THICKNESS deep and centred on the band midpoint (so THICKNESS is the opaque-core depth, **not** an edge transition; C1/IA1 970–1124 ±30 → total only in 1032–1062). - `src/Effects/Puffer.cs` — the original engine's billboard-particle emitter, data-driven from a zrdr `PUFFER_STATE` block. `PufferState.Load(zrdr, file, name)` DFS-searches an effects reader (flame_ball.json, fire.json, pufftrails.json, … same schema) for the fully-defined puffer (has `NUMBER`, not a stop-stub) and parses its params (per-axis random velocity, friction, size/lifetime ranges, growth factor, deviation, and the `TEXTURE_SEQUENCE` flipbook). `Puffer.Create(state, textures)` builds a horizontal atlas from the flipbook PNGs and returns a CPU-simulated emitter drawn as ONE `MultiMeshInstance3D` (per-instance transform + custom data): a small spatial shader billboards each quad toward the camera (hand-rolled billboard_keep_scale, since MultiMesh has no built-in), picks the flipbook column from `INSTANCE_CUSTOM`, and additively blends (`blend_add`, `depth_draw_never`) — the fire frames are alpha-masked with black edges, so additive gives a soft glow and no quad edge. The CPU sim honours the reader exactly: exponential friction, `Lerp(1,growth,age/life)` size growth, and the non-uniform per-frame flipbook timing; a life-fade envelope (`FadeIn`/`FadeOutStart`) is the only render nicety not in the data. `Burst(worldPos)` (sets `TopLevel` so it stays put in world space) emits `Number` sprites per `TimeInterval` for the caller's active window (default 0.3 s = large_fireball's STOP time); `Clear()` wipes all live particles. **Run-2 item 10c/d extensions:** (1) **trail emitters** — states with `DISTANCE_INTERVAL` (dense_firetrail's smoke/fire, black_smoke) are driven via `TrailAdvance(worldPos)` each frame: one sprite per interval of motion with carry across frames, world-anchored (the trail stays behind the plane); `FindInReader` now accepts NUMBER **or** DISTANCE_INTERVAL as "fully defined". `TrailBurnAt(worldPos, dt, speedMps)` (2026-07-19, the damage lab) is the parked-plane variant: it spends `speedMps` of *virtual* motion per second at a fixed point through the same carry/pool/spawn path, so a distance-interval trail reads as a flickering in-place fire (the puffs' own ±0.8 m/s random velocity + growth provide the motion). (2) **static TEXTURES pools** (smoke101–103): each puff picks a random atlas column at spawn and keeps it (vs the flipbook's age-keyed frames). (3) **COLORS age-ramps** (`[lifeFrac, r,g,b, a]`, rgb 0–255 by the weather.json integer rule): evaluated per particle per frame into the MultiMesh instance color; ramp presence ⇒ **blend_mix** (black smoke is invisible additively), no ramp ⇒ blend_add as before (ramp alpha replaces the FadeIn/Out envelope). (4) Two shader fixes for every effect: a **quad-rim fade** (fire_f01 leaks border pixels up to 247 — grown quads painted faint additive rectangles over dark ground) and **soft particles** (`hint_depth_texture` fade over the last 1.5 m of depth gap — billboards tilted by the high chase camera dip into terrain/walls, and the depth test cut them with hard straight lines; very visible on the 12 m wreck fire, diagnosed via crash screenshots).
- `src/Effects/CloudPuffs.cs` — the ambient cloud puffs: a field of very soft, translucent `cloud1`/`cloud2` billboard sprites the plane flies through at altitude (the wisps drifting past in `OriginalScreenshots/C1 IA1 Cloud Puffs and Moon.png`). **Why synthetic, not the world's own sprites:** C1 places ~600 `cloud1`/`cloud2` sprite quads, but they are **clustered near the airfield** (verified — two far map corners at band altitude render bare) and world-fixed, so most of the map has no clouds at altitude. No zrdr defines an ambient emitter (only crash-style `PUFFER_STATE` readers exist), so this is a hand-tuned field parameterized by the data we do have: the `CLOUD_COVER` band anchors the layer's altitude, the weather `WIND` drives a slow drift (every feel constant is TUNE, playtest-calibrated). **Model:** a fixed pool of world-anchored sprites in a cylindrical shell around the camera, **anchored in Y to the cloud band** (world-fixed altitude — you climb up into the layer then out over it, like a real layer) while the field follows the plane in X/Z; a puff the plane flies past horizontally recycles to the leading edge (spawns ahead of the nose so the plane flies into fresh clouds), so the field is endless. Alpha fades to 0 at the shell edge (recycled puffs fade in, never pop) and by vertical distance from the camera (`VertFull`/`VertFade` — clear well below/above the layer, so low-altitude flight has no clouds and climbing above leaves scattered wisps below). Drawn as ONE `MultiMeshInstance3D` (one draw call): a spatial shader billboards each quad toward the camera (hand-rolled keep-scale, like Puffer), applies a per-instance roll (variety), picks cloud1/cloud2 from `INSTANCE_CUSTOM`, and **alpha-blends** (`blend_mix`, `depth_draw_never`, `fog_disabled` — soft translucent clouds, unlike Puffer's additive fire glow). Since Run-2 item 4 the fragment shader also carries SceneBuilder's **cylindrical distance-fog term** (the same `csky_fog_*` globals + `mix` toward the fog colour), so a puff at the shell edge fades into the fog wall like the terrain below it; the `fog_disabled` render mode stays (it only turns off Godot's *built-in* fog — ours is custom). *In practice the visible effect is negligible in the flyable zones:* the 620 m puff shell sits almost entirely inside the fog's clear near-range (`FOG_RANGES.x`/2 ≈ 500 m in C1/C4 zone2 ⇒ shell-edge puffs fog only ~2 %, near puffs unchanged), so it is a correctness/consistency fix (removing the old fog immunity), not a big look change — the "crisp white against the fog wall" was always the world sprites. The cloud textures are fairly opaque (mean α≈0.43, p90≈0.87), so overlaps saturate fast — `BaseAlpha` is kept low (0.06–0.13) so they read as translucent veils not a solid white ring; `Count` 12, `Radius` 620 m. `Create(textures, wind, bandBottom, bandTop)` builds the 2-frame atlas (null if the textures are absent); `Update(dt, cameraPos, cameraForward)` advances the field each frame (self-gates via the vertical fade — safe to call at any altitude). PlaneViewer builds it in `SetupWeather` (only when the mission has a `CLOUD_COVER` band) and drives it in `_Process` from the flight camera. `--fly`, or static `--chapter` + `--sky-zone` for deterministic `--campos` verification.
- `src/Effects/Precipitation.cs` — rain/snow from the mission weather.json's precipitation block (M2-polish Run-2 item 5; `WeatherState.PrecipData` — C4 SNOW, C1C/C2B RAIN, none in C1/C5 IA1). **Model — a camera-following field the plane flies through, entirely GPU-driven.** One `MultiMeshInstance3D` (one draw call) of N small quads; each instance carries a fixed random seed in `INSTANCE_CUSTOM` (base fraction [0,1)³ + a flutter phase), set once. A spatial shader turns that seed into a world position that (a) falls + drifts over `TIME` (`seed·cell + fall_vel·TIME`) and (b) wraps into a box **centred on `CAMERA_POSITION_WORLD`** (`mod(rel + box_half, cell) − box_half`) — so the field is world-anchored (the plane's own motion carries the particles past = correct parallax), infinite, and seamless (dense uniform particles make the per-cell wrap invisible). The whole animation runs from the `TIME` + `CAMERA_POSITION_WORLD` built-ins, so there is **zero per-frame CPU** — `Create` builds it and it plays itself (no `_Process`/`Update`). Because the shader positions everything around the camera far from this node's origin (where the actual identity instance transforms sit), a **world-sized `CustomAabb`** (±40 km) keeps Godot from frustum-culling the whole MultiMesh — the clean alternative to per-frame moving the node. **SNOW** = small camera-billboard flakes (`INV_VIEW_MATRIX` right/up, per-instance size from the seed) with a gentle per-instance horizontal flutter (`sin/cos(TIME·freq + phase)`, so they don't fall in lockstep). **RAIN** = thin streak quads axially billboarded **along the fall direction** (`normalize(fall_vel)` as the long axis, thin axis facing the camera; length ∝ fall speed) — the data's GRAVITY+WIND world velocity, *not* the plane-relative velocity (rain visibly coming at you when flying fast is a nicer look but not what the data says — a documented TUNE follow-up pending the user's A/B). Alpha = `peak_alpha` (ALPHA_GRADIENT.x) × a **near-fade** (particles within `near_fade` ≈3 m of the camera fade in, so a flake on the chase-cam "lens" doesn't blow up into a blob — natural in a cockpit, distracting third-person) × a radial box-edge fade (no hard cubic boundary) × a **cloud-band gate** (`1 − smoothstep(CloudBottom, CloudTop, particleY)` — precip only shows **below** the CLOUD_COVER band, since it falls from the cloud base; none above the overcast — user-requested 2026-07-18; a huge sentinel band disables it when a mission has precip but no cloud band). No distance-fog term: unlike the cloud sprites (km-scale, out to the fog wall), the ~30 m precip box sits entirely inside the fog's clear near-range (`FOG_RANGES.x`/2 ≈ 250–500 m), so a fog mix would provably never fire. `COLOR` is converted **sRGB→linear** for the unshaded ALBEDO (like FOG_COLOR), so the data's byte value renders back correctly. The sprites are **procedural** (a soft radial dot / a soft vertical streak generated in `MakeFlakeTexture`/`MakeStreakTexture`) — the original rendered untextured coloured line/point primitives, which no texture archive carries, so a tiny generated sprite is the faithful, asset-free stand-in; no `TextureArchive` dependency. `Create(precip, cloudBottom, cloudTop)` → null if the mission has no precip. Body rates from control torque × reciprocal inertia vs `ang_momentum_damp`, scaled by **per-axis calibration constants** (Run-2 item 12, 2026-07-19, replacing the user's interim global `rotationTune` ×2): `PitchTune` 0.75 / `YawTune` 1.32 / `RollTune` 2.12 (TUNE), solved from the user's stopwatch measurements of the original Bloodhawk at full throttle — 360° roll in 2 s, sustained full-pitch 360° at 90° bank in 11 s, full-rudder 360° in 30 s — via steady rate = torque·recInertia·Tune/damp (× the speed-dependent `eff` on yaw only, 0.4 at cruise where the yaw datum was taken) and time-to-360° ≈ 1/damp spin-up + 2π/rate. Verified by scripted `--hold` telemetry: steady rates 3.50/0.58/0.21 rad/s exactly as computed (yaw at cruise). Note the original bleeds speed in the sustained pitch turn and may couple pitch rate to speed — ours is constant, matching the 11 s average (open fidelity question). Side effect of the pitch cut (1.56→0.58 rad/s): a full-stick stall now settles where the stall drop balances the elevator (~22 m/s, nose ~28°) instead of pinning at the horizon-cap — a milder cousin of the accepted arcade-hang artifacts; the stall drop still dominates below that equilibrium and the horizon cap still holds (regression-run verified). Translation (**vector integration, 2026-07-17 second pass**): thrust (along the nose), drag (against the motion) and gravity integrate on the velocity **vector** `v = VelocityDir·Speed`, so the speed can pass **through zero** — a vertical zoom tail-slides out downward instead of freezing mid-air at a clamped 0 (user-reported: plane stopped in the air with the HUD mph creeping back up; the first-pass scalar model clamped `Speed ≥ 0` and re-accelerated along a stale path direction). **Lift fraction** = `min(1,(v/liftSpeed)²) × |planeUp·worldUp|` (wingVert — 1 level *or inverted* (arcade), 0 knife-edge); gravity is split about the path and its **cross-path component is canceled by the lift fraction** — the deficit is the sink: vanishes at full lift, drops the plane when slow or knife-edge. The **nose-chase alignment** (velocity slerps toward the nose) scales with airspeed (controls mush as airflow dies) *and* wingVert (`KnifeAlignFloor` 0.35 — the chase is the lift force turning the velocity, so knife-edge equilibrium sits visibly ~10° below the nose: the sink). **Stall** (below 0.3·fd_speed): the nose is pulled toward **world-down** via a great-circle rotation about nose×down (attitude-independent — works inverted; replaces the old body-frame pitch-rate bias), rate `stall_mag × StallNoseRate × depth` — deep-stall rate exceeds full-elevator authority, so the drop is decisive until airspeed recovers. **While stalled the nose can NOT be raised over the horizon at any bank angle** (original behavior, user-observed 2026-07-17): after the frame's rotations its world elevation is capped at `max(horizon, frame-start elevation)` — pulled up from below it parks at the horizon; caught nose-high by the stall it can only come down (so a low-speed full-pull loop breaks at the top instead of completing). **Drag is a quadratic + linear blend** (`LowSpeedDragBlend` 0.35 TUNE, normalized so drag(fd_speed) = max thrust — the full-throttle equilibrium stays exactly `fd_speed` for any blend): the linear share is the low-speed air-resistance bite (user-reported: idle level flight barely decelerated on the pure-v² tail; now 120 mph idles down to the ~89 mph stall in ~9 s and settles into a natural nose-dropped glide). **Climb retention**: gravity's along-path bleed is scaled `ClimbGravityScale` 0.6 when climbing (full when diving) — an 11° full-throttle Bloodhawk climb holds ≈122 m/s; the exact factor awaits the user's measured original-game climb curve. Verified via segmented `--hold` telemetry runs: vertical zoom → 12 m/s → nose-over → dive recovery (no hover); knife-edge path −10°, −174 m in 15 s; cruise/level regression byte-identical behavior (wingVert 1 → all new factors are exactly 1). Hand-tuned scale constants marked TUNE. **Near-parallel path-chase fix (2026-07-19, found while verifying item 5 — it bit single player identically):** the velocity-chases-nose term ended in `VelocityDir.Slerp(nose, …)`, and *cruise is exactly the degenerate case* — `Slerp` derives its rotation axis from the cross product of the two vectors, whose absolute float error (~1e-7) swamps a sub-degree angle, so the normalized axis fails Godot's `IsNormalized` check and `Rotated` **throws**. The exception propagated out of `_PhysicsProcess`, aborting the whole frame before the position commit: a plane holding straight and level simply stopped flying, ~1 error per physics frame forever (reproduced deterministically by `--hold=0,0,0,1` from a `--spawn-at` — the plane froze at a fixed Z and the telemetry stopped). Guarded by branching on `pathDot > 0.999f` (≈ 2.5°) to a normalized lerp, which needs no axis and differs from the slerp by well under a thousandth of a degree at that separation; the pre-existing `> -0.999f` anti-parallel guard stays. Do not "simplify" this back to a bare Slerp.

- `src/Flight/PlaneCollider.cs` — the flying aircraft's collision silhouette (M2-polish item 8; refit Run-2 item 10a): 5–8 plane-frame **boxes** that FlightController sweeps along each physics frame's motion so wingtips and tail collide, not just the old center ray. `Build(planeModel)` derives them once from the built model's mesh **triangles** (hidden subtrees — wing flares, the 10c damage panels — excluded; nose prop blur discs excluded, autogyro rotor discs included: that plane's wing). (2) **Screen-space de-cluttering**, nearest-first on a 108×26 px grid with a 3×3 neighbourhood check (own-cell only would allow two labels a pixel apart); this — not `Radius` — is the readability limiter, which is why `Radius` can be a generous 1500 m. The first cut's 300 m put the ground out of range entirely, since the flight camera sits hundreds of metres up. Off-screen and behind-camera nodes are rejected before claiming cells, or they burn label slots on invisible text. (3) The flown aircraft is **deprioritised** (ranked after every in-range world node, not excluded): it sits metres from the camera while the world is hundreds away, so nearest-first otherwise spends every label on the plane you are sitting in — but a misplaced node can be on the aircraft too, so its labels still appear wherever the world leaves room. Selection runs on a 0.35 s timer, not per frame (positions are world-static and Label3D billboards itself), and the candidate walk is redone on the same timer because the flight tree genuinely changes — MapEdgeExtender adds and drops border tiles on cell crossings. Builds no nodes at all until first switched on, so an untouched session renders identically.
- `src/UI/MeshLab.cs` — the static viewer's geometry/shading lab (`--viewer`, key **M**, 2026-07-20). **Why it exists:** "this patch looks wrong" is not diagnosable from a screenshot — a normal pointing the wrong way, a polygon single-sided that should be double-sided, a polygon falling back to a flat face normal, and a texture that was simply never painted all look alike on a dark model. The lab separates them by changing exactly one at a time. **Widgets:** normal lines (per-face at the centroid, or per-corner — ~3× the lines and a hairball on a small aircraft, hence per-face default), coloured by **provenance** (stored vs flat fallback × sidedness), direction (xyz→rgb), or winding agreement; wireframe with **hard smoothing seams** picked out (an edge whose adjacent triangles disagree about the normal at a shared position — these outline flat/smooth patch boundaries directly), plus Godot's viewport wireframe as a separate toggle; the `PlaneCollider` boxes coloured by the `PlaneDamage` part they map to, **split at x=0** for a slab that straddles the centreline since `MapStruckPart` resolves those by impact point (a single colour would be a lie); ambient/sun energy, XYZ sun direction, and a **headlight** (light rides the camera — the sharpest normals test there is, since every surface facing you is lit by definition and one that stays dark is unambiguously wrong). **Override cyclers:** `cull` (as-data / all-double / all-single / inverted = `cull_back`, which tests the project's "visible side is the CCW loop" convention directly) × `normal source` (as-data / all-flat via screen derivatives / all-smooth via a CPU re-weld / negated) — independent axes, 16 combinations. **Three load-bearing details.** (1) Built **after** the plane joins the tree: it reads geometry back through `GlobalTransform`, which on a detached node returns identity *and logs an error per call* rather than walking the subtree — the first cut produced hundreds of lines of backtrace, violating the run-2 log-hygiene rule. (2) Override materials replicate SceneBuilder's vertex stage **verbatim** (same `skip_vertex_transform`, same `depth_bias`/`node_bias` scale-toward-eye); without that the coplanar decals z-fight the moment you toggle anything and every comparison is worthless. (3) It **seeds its light sliders from the scene** rather than a default — writing a hardcoded direction at `_Ready` re-aimed the sun and broke the byte-identical `--viewer` screenshot (caught by md5, fixed by only writing lighting when `--debug-mesh` asked for it). **Override slots are bounds-checked against the INSTANCE, not the mesh** (user-reported crash, same day): `MeshInstance3D` sizes its `surface_override_materials` array when the mesh is assigned, so the two counts can disagree — and Godot checks the array. A surface carrying no triangles commits to a **0-surface** mesh, so `AllSmooth` swapping one in left the array at size 0 and the next `SetSurfaceOverrideMaterial(0, …)` errored per call. Guarded twice: `SmoothMesh` refuses to swap in a 0-surface mesh, and `SetOverride` checks `GetSurfaceOverrideMaterialCount()` and *recovers* by re-assigning the mesh to force the resize rather than skipping — skipping would silently leave a surface un-overridden, i.e. half an A/B, and a conclusion drawn from that would be wrong. `--debug-mesh=cycle=N` exists to make this path scriptable; it reproduces the crash on unfixed code (4 occurrences) and passes on fixed code, which is the only reason the regression test is worth anything. **Provenance is inferred, not plumbed:** SceneBuilder records nothing, and widening its API for a debug view is not worth it, so a triangle counts as flat when its three corner normals equal each other and the winding normal — exactly what the fallback produces. A genuinely flat-shaded file polygon reads as flat too; tolerable for a diagnostic and stated in the panel. This lab is what diagnosed the inverted aircraft normals: culling was eliminated first (the wing stayed dark in all four cull modes, 6.4/7.8/6.4/6.6), then `ambient=off` + `dir=0/-1/0` gave the controlled sun-up-vs-sun-down test that settled it.
- `src/PlaneViewer.cs` — Main.tscn root script: orbit camera, lighting. **Session lifecycle (M2.5 item 4 — the launchscreen's in-process world rebuild):** `_Ready` parses the args, registers the global shader params, logs the gamepad roster + subscribes `Input.JoyConnectionChanged` (one connect/disconnect line per device — the hotplug ground truth in every mode; note the engine also re-fires the signal for already-present pads shortly after startup), and sets up lighting + the (persistent) camera **once**, then either shows the launchscreen (`ShowLaunchMenu` — when no content-selecting arg was passed, or `--menu`) or calls `StartSession` directly. `StartSession()` is the build formerly inline in `_Ready`: it makes a fresh `_worldRoot` Node3D and hangs **everything a session builds** under it (world/plane/horizon/whiteout/puffs/precip/controller — base paths read as locals, the chapter-dependent gamez/texture/mission paths recomputed from `_chapter` so a new launchscreen chapter takes effect), returning true/false. The menu's `Launch` → `StartSessionFromMenu` sets `_chapter`/`_planeName`/`_stunt` (+ derives `_scenario` from the mode unless `--scenario=` was pinned) and calls `StartSession`, so menu and CLI share exactly one downstream build path. `ReturnToMenu` (Esc from a menu-launched flight, or a failed menu build) `QueueFree`s `_worldRoot` and **nulls every cached session ref** (`_plane`/`_horizon`/`_deck`/`_whiteout`/`_puffs`/`_precip`/`_edgeExtender`/`_weather`) so `_Process`'s null guards skip them the one frame before the deferred free lands, then reshows the menu; a CLI-launched flight's Esc still quits (`_menuDriven` gates it). **The first in-process world rebuild in the project** — verified by a scripted C1-stunt → teardown → C4-free-flight rebuild (clean, different chapter/plane/mode, no exception). Gotcha that makes it safe: the `RenderingServer.GlobalShaderParameterAdd` calls stay in `_Ready` (once) — `SetupWeather` only `Set`s them each session, so the rebuild never double-Adds (which would error). `PreferUnzipped` was hoisted from a `_Ready` local to a class static (used by both `_Ready` for base paths and `StartSession` for the per-session chapter paths). **F12** (any mode — orbit view or free flight) saves the current frame to a timestamped PNG under the repo's git-ignored `Screenshots/` folder (`SaveScreenshot`; full viewport, HUD included) — distinct from the automated `--screenshot=<path>` one-shot. **F11** (any mode) prints the current camera pose as ready-to-paste `--campos=`/`--lookat=` args (`PrintCameraPose`; orbit-mode look-at = `_orbitCenter`, `--fly` = a point one unit ahead along the view ray — either reproduces the framing since FrameCamera reconstructs pitch/yaw from the pos→look-at direction) — for turning a hand-framed view into a deterministic `--screenshot` run. **Burst capture (`--shots=N`, for z-fighting debugging):** after the `--frames` warm-up, the `_Process` capture block grabs one frame per tick for N ticks (indexed files via `IndexedShotPath`, `foo_00.png`…), then quits; N=1 is byte-identical to the old single-shot at the verbatim path. Because the viewport `GetImage()` reflects the *previous* frame's render, `ApplyShotJitter` is applied *after* each save (for the next tick's render): file `_00` is the un-jittered baseline, `_01..` carry the dither. **`--jitter=<deg>` (default 0.15° when N>1, static mode only):** a per-frame micro-orbit of the camera about the framed point (`_orbitCenter`) — a dead-still camera renders bit-identical frames, so nothing z-fights across the burst; the dither rotates the eye a hair (golden-angle spread over `_shotIndex` so consecutive frames differ maximally) so coplanar surfaces re-decide the depth test. It rotates the whole camera rigidly about the pivot (same rotation applied to the eye offset and the basis → aim preserved exactly, subject stays centred). Skipped in `--fly` (FlightController owns the camera each frame, and the plane's own motion already surfaces the fight). Verified via md5: jitter-off burst → all frames identical; jitter-on → `_00` matches the still baseline, `_01..` all distinct. In `--fly` mode also adds the original skydome (`WorldBuilder.BuildHorizon`), scaled **2.5×** and re-centered on the camera every frame in **all axes** (a zero-parallax backdrop; full anchoring keeps the moon at its designed ~28° elevation against the dome-cap color its painted background matches — y-anchoring at 0 slid it into the brighter horizon band when climbing). The scale trick makes plain depth-testing sort it behind everything: a camera-centered dome is visually scale-invariant, and at ~22 km radius it is past the farthest terrain (~17.4 km corner-to-corner) but inside the 40 km far plane. Static `--chapter` viewing does NOT render the horizon (an outside orbit camera would see the double-sided dome enclose the world) unless `--sky-zone` is passed explicitly (useful with `--campos` inside the map for deterministic sky-verification screenshots). When flying or in static weathered views (`_fly || _skyZoneExplicit`) it creates the map-edge continuation (`builder.CreateEdgeExtender(clutterBuilder)` → `MapEdgeExtender`, Run-2 item 7 — a rolling window of repeated border tiles + clutter past the map boundary) and re-centers it each `_Process` via `_edgeExtender?.Update(_camera.Position)`; plain `--chapter` orbit viewing stays extension-free (an honest data view — no invented geometry). **Weather** (`SetupWeather`, applied whenever the world+dome are shown — `--fly`, or static `--chapter` with `--sky-zone`): loads the flown mission's `weather.json` (`WeatherState.Load`) and (1) sets the distance-fog global shader params (`csky_fog_color`/`csky_fog_range`/`csky_fog_alt`) for the rendered `--sky-zone`, which every world + aircraft surface picks up (the fog globals are registered with a no-op range at startup so unfogged modes are unaffected), plus the **`csky_world_light`** scalar (Run-2 item 6: the mission's SUNLIGHT world-brightness `WeatherState.WorldLight`; registered default 1.0 = fullbright for unweathered modes, set from the zone's factor but **linearised** first — `Color(f,f,f).SrgbToLinear().R` — so the fullbright shaders' linear-space `ALBEDO ×` lands the dimming in gamma space, matching the DX7 texel×vertex×light chain: the C1 deck 210→169) — `FOG_COLOR` is converted **sRGB→linear** before it's set (it is a DX7 framebuffer value: the original's fully-fogged pixels are exactly 0.69·255 = 176 gray, measured flat in `OriginalScreenshots/C1 IA1 Cloudcoverage 1.png`; feeding 0.69 raw into Godot's linear pipeline rendered saturated fog as washed-out 216), and `FOG_RANGES` is halved (`fogRangeFactor` 2, the user's screenshot calibration — predates the sRGB fix, so it deserves a fresh in-game A/B; factor 1 makes the overcast's texture persist further toward the horizon), and (2) if the mission has a `CLOUD_COVER` band, builds a full-screen `ColorRect` **whiteout** overlay (its own CanvasLayer below the flight HUD) whose opacity is driven each frame in `_Process` from `WeatherState.WhiteoutAmount(cameraY)` (the trapezoid above — 0 at the band edges, full opaque core centred on the midpoint). Its color is `WhiteoutColor` (near-white — inside a cloud reads near-white, not the 0.69 fog gray; TUNE; ref `OriginalScreenshots/C1 IA1 whiteout at height.png`). **Cloud deck follow** (the deck-move block in `_Process`, when a cloud band exists): re-anchors WorldBuilder's `CloudDeck` under the player each frame — centered on the camera x/z and pinned to a fixed altitude at the **whiteout-band centre** (`(CloudTop+CloudBottom)/2`). So you climb toward it as a fixed overcast ceiling, pass through it exactly where the whiteout is fully opaque (the ceiling→floor transition is hidden), and it sits as a floor below once you're above the band — the model the user picked after playtesting. The deck's original AABB centre (`_deckCenter`, computed once after it's in the tree) is subtracted so the sheet re-centres on the target. Only moved when weather is loaded (`--fly`, or static `--chapter` + `--sky-zone`); otherwise it stays at its data altitude, so plain `--chapter` orbit viewing is unchanged. **Ambient cloud puffs** (`SetupWeather` builds `Effects.CloudPuffs` when the mission has a `CLOUD_COVER` band; `_Process` drives it from `_camera.Position` + look direction): the soft wisps that drift past the plane at altitude everywhere on the map (the world's own `cloud1`/`cloud2` sprites are clustered near the airfield only — see CloudPuffs.cs). **Precipitation** (`SetupWeather` builds `Effects.Precipitation` when the mission's weather.json carries a precipitation TYPE block, passing the CLOUD_COVER band so it only falls below the overcast): rain/snow the plane flies through — self-animating from the shader's `TIME` + camera built-ins, so unlike the puffs it needs **no** `_Process` driving (see Precipitation.cs). **Compass:** the `--fly` assembly also builds `CompassTape.Build(textures)` while the chapter texture archive is open and hands it to the FlightController (`Compass` field), which adds it to the HUD canvas and feeds it the heading. **Gauges:** likewise `GaugeCluster.Build(planesGamez, plane, textures, stats.DestroyableParts)` → `controller.Gauges`, with `PartFraction` bound to the controller's `PlaneDamage`; in the damage lab a second Build goes to the `DamageLab` ctor instead (slider-driven). **Damage lab (`--damage[=part:frac,…]`, 2026-07-19):** static `--plane` mode only (ignored with a note when `_worldMode` — flight gets damage from collisions); builds the plane with `damagePanels: true`, loads `PlaneStats`, constructs the smoke/fire pair + an **8**-emitter panel-trail pool (flight uses 4; 8 = every pdp panel can burn at once) via the shared `MakePuffer` helper (the former fly-branch local function, hoisted static so both assemblies use it — fly behavior unchanged), and adds a `DamageLab` driving a `DamageVisuals` (see those bullets). Presets parse in `ParseDamagePreset` (`part:frac`, >1 = percent, clamped); a plane whose def has no `destroyable_parts` logs and skips the lab. **Stunt mode (`--stunt`, M2.5 item 1):** forces `--fly` + the `stunt_flying` spawn list (unless `--scenario=` was set explicitly), and after the flight assembly builds `StuntMission.Load(gamez, missionZrdrPath, Messages.Load(messagesPath))` (the *world* gamez, so the `dzN` positions resolve; `--messages=` defaults to `extracted/messages.json`) → `controller.Stunt` (null → a "flying free" warning); on success it also builds the objective `MarkerHud.Build(controller.Stunt, _camera)` into `controller.Marker` (item 2). **`--debug-dzpaths`** builds the world's skipped `dzpaths` route ribbons via `WorldBuilder.BuildDzPaths()` for inspection. **`--spawn-at=x,y,z` / `--spawn-dir=x,y,z`** (debug) override the mission spawn in `ChooseSpawn` — place the plane exactly for deterministic scripted runs. **Splitscreen (M2.5 item 5):** `StartSession` calls `BuildRigs(_fly ? _players : 1)` **first**, because everything camera-anchored built later is per-rig. One player takes the existing main-viewport camera with `VisualLayer` 0 — no SplitScreen node, no narrowed cull masks, nothing else changed, which is why the 1P path stayed a clean regression.
